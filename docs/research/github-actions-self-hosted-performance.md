# GitHub Actions performance on the self-hosted Mac

Researched 2026-09-22. Scope: GitHub.com Actions on AutoTM's persistent macOS self-hosted runner. The first section measures this repository; later sections summarize external source research.

## What AutoTM's runs show

The [CI workflow](../../.github/workflows/ci.yml) and [PR workflow](../../.github/workflows/pr-checks.yml) use the same `tm-build-mac` runner. Each checks out the repository, installs all pnpm workspace dependencies, generates Prisma, then runs lint, typecheck, and tests. Main also builds. Neither workflow enables `setup-node`'s pnpm cache; the [bundle workflow](../../.github/workflows/bundle.yml) does.

The PR install log reports **2,044 packages reused, zero downloaded**. The later main install reports **zero reused, 2,044 downloaded**. This establishes that dependency retrieval can dominate a cold run. It does **not** establish why the pnpm store was unavailable then. Inspect store path, free space, cleanup/pruning, and whether both jobs use the same user and pnpm version before changing caching. The Mac had about **11 GiB free** on a 460 GiB data volume when inspected on 2026-09-22; the user's `~/Library/pnpm/store` was about **8.9 GiB**. Low free space is a plausible contributor to cache instability, not a proven cause.

Checkout already uses `fetch-depth: 1`, no tags, LFS, or submodules. In the sampled logs, `git fetch` itself took about **2 seconds**; `git clean -ffdx` took about **10–12 seconds** and explicitly removed `node_modules`, `.turbo`, build outputs, and generated files. That is why workspace-local Turbo cache cannot survive a normal checkout. Disabling checkout cleaning to preserve these directories risks stale generated files and cross-job contamination. If caching Turbo outputs is worthwhile, put its cache outside the checkout directory or benchmark a remote cache. [PR log](https://github.com/bagtyyarkovusov/auto.tm-rewrite/actions/runs/35582538081); [main log](https://github.com/bagtyyarkovusov/auto.tm-rewrite/actions/runs/35596238264).

The 64-second setup on the sampled PR includes two failed `codeload.github.com` action downloads and their 27-second and 21-second backoffs. This is direct evidence of an intermittent GitHub connection issue, separate from source checkout. The normal setup was 11–12 seconds in the two sampled main runs. The test step remains about **one minute** even with a warm dependency store; local CPU/test work is therefore the next bottleneck after eliminating cold downloads. [PR log](https://github.com/bagtyyarkovusov/auto.tm-rewrite/actions/runs/35582538081).

### Recommended experiments, in order

1. **Diagnose cold installs.** Record `pnpm store path`, pnpm/Node versions, free disk, and install's reused/downloaded counts for several CI runs. Keep the pnpm store at a stable path outside `actions-runner/_work`. Investigate any cleanup task or store-path drift; reclaim disk space deliberately rather than deleting the active store. A warm install is already about 11 seconds, so a repeatable local store has the largest demonstrated upside.
2. **Measure network routes separately.** Time access to `codeload.github.com`, the npm registry, and GitHub checkout. Use the runner's `config.sh --check` for GitHub endpoints. The two action-download retries show a routing problem worth testing; faster Git fetch alone would save only a few seconds in these samples.
3. **Benchmark the 60–90-second test step.** Use test-runner timing and Turbo summaries to find expensive suites and cache misses. The current checkout removes `.turbo` each time, so cross-run task caching is absent unless configured elsewhere. Keep integration-test isolation and correctness intact when splitting or caching tests.
4. **Evaluate checkout and action overhead only after 1–3.** The current shallow fetch is already small. Measure whether action-download failures recur. The bundle's GitHub-hosted pnpm cache may add a remote restore/save that a persistent local store does not need; compare bundle runs before changing it.

For a before/after comparison, gather at least five warm and five cold/changed-lockfile runs, report median and slow tail, and track queue time separately from job execution. These sample sizes are a practical proposed experiment, not a GitHub requirement. Do not infer a general speedup from one run.

## The network path is more than repository download

The runner connects outward to GitHub to receive jobs. GitHub lists separate domains for essential coordination (`github.com`, `api.github.com`, `*.actions.githubusercontent.com`), action code (`codeload.github.com`), artifacts/logs/caches (`results-receiver.actions.githubusercontent.com`, `*.blob.core.windows.net`), runner updates, packages, and LFS. Thus a slow job may be waiting on source checkout, action downloads, package registry traffic, a remote cache restore/save, artifacts, or the runner's own update—not necessarily the Git repository. The runner needs outbound HTTPS on port 443. The runner's built-in `config.sh --check --url ... --pat ...` can verify access to GitHub's required services. [Self-hosted runner reference](https://docs.github.com/en/actions/reference/runners/self-hosted-runners); [monitoring and troubleshooting](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/monitor-and-troubleshoot).

GitHub's Actions dependency cache is **remote even on a self-hosted runner**: GitHub.com stores cache entries in GitHub-owned cloud storage. A restore and subsequent save can therefore use substantial WAN bandwidth, compression time, and disk I/O. It should be measured against a warm local package store before assuming it helps. Customer-owned cache storage is documented for GitHub Enterprise Server, not GitHub.com. GitHub's cache is scoped by key, version, and branch; excessive key churn or large caches can cause eviction and repeated transfers. [Dependency caching concept](https://docs.github.com/en/actions/concepts/workflows-and-actions/dependency-caching); [dependency caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching); [actions/cache](https://github.com/actions/cache).

`actions/setup-node`'s `cache: pnpm` caches the **pnpm store**, not `node_modules`, using `actions/cache` under the hood. Its implementation gets the path from `pnpm store path --silent`. On a persistent Mac, a local pnpm store may already survive across jobs; the remote cache may then be an extra transfer. This is a hypothesis to benchmark, not a universal recommendation. The Node toolchain itself can be locally cached: `setup-node` checks its local tool cache first when `check-latest` is false (the default); a miss downloads Node. `check-latest: true` can add network work. [setup-node README](https://github.com/actions/setup-node/blob/main/README.md); [advanced usage](https://github.com/actions/setup-node/blob/main/docs/advanced-usage.md); [cache implementation](https://github.com/actions/setup-node/blob/main/src/cache-utils.ts).

## Checkout levers and limits

`actions/checkout` defaults to `fetch-depth: 1`, does not fetch tags, LFS, or submodules by default, and cleans the worktree with `git clean -ffdx && git reset --hard HEAD` before fetching. `fetch-depth: 0` fetches all branches and tags; avoid it when a step does not need history. The action supports partial clone with `filter` and sparse checkout, which can reduce transfer for a job that truly needs only some paths. A monorepo-wide build/test may still need most files, so estimate from actual checkout duration and repository object size first. Disabling `clean` solely to keep `node_modules` weakens isolation and can retain stale generated files; keeping reusable dependency data outside the checkout worktree is a safer experiment. [actions/checkout README](https://github.com/actions/checkout/blob/main/README.md).

Path filters can skip entire workflows for changes outside relevant paths, but GitHub warns that skipped required workflows remain pending and can block PR merges. If this CI check is required, job-level conditional no-op success or a separate required gate needs design and verification. [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushpull_requestpull_request_targetpathspaths-ignore).

## Uploads and macOS-specific constraints

Artifact uploads are another outbound transfer. `actions/upload-artifact` defaults to compression level 6; for already compressed, large binary files, its README recommends level 0 to avoid expensive compression. Whether that helps elapsed time depends on the local CPU versus upload bandwidth, so compare both settings with the actual artifact. Prefer to omit artifacts that no later job or human needs. [upload-artifact README](https://github.com/actions/upload-artifact/blob/main/README.md#altering-compressions-level-speed-v-size).

GitHub Actions service containers and container actions on **self-hosted runners require Linux and Docker**. A macOS runner cannot rely on Actions `services:` to accelerate or host Postgres/Redis in that mechanism; if tests use Docker on Mac, that is a separate local Docker runtime concern. [Self-hosted runners reference](https://docs.github.com/en/actions/reference/runners/self-hosted-runners); [workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idservices).

For a proxy or VPN, configure the runner's `https_proxy`/`http_proxy`/`no_proxy` **before** starting it, and restart after changes. GitHub recommends lowercase variable names on macOS; when both cases are present, the runner uses lowercase. Test routing per endpoint rather than assuming the proxy improves all traffic. [Using proxy servers with a runner](https://docs.github.com/en/actions/how-tos/manage-runners/use-proxy-servers).

## Measure before changing the workflow

The official workflow-jobs REST API exposes each job and step's `started_at` and `completed_at`, including setup, checkout, cache restore, package install, build/tests, post-job cache save, and completion. Compare at least several runs with the same lockfile and similar repository state; distinguish queue time from execution time and a cold run from a warm run. If standard logs cannot explain a delay, `ACTIONS_RUNNER_DEBUG=true` adds runner and worker diagnostic logs to the run archive; `ACTIONS_STEP_DEBUG=true` adds step details. The runner's `config.sh --check` helps separate routing/connectivity from transfer speed. [Workflow jobs REST API](https://docs.github.com/en/rest/actions/workflow-jobs); [debug logging](https://docs.github.com/en/actions/how-tos/monitor-workflows/enable-debug-logging); [runner connectivity check](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/monitor-and-troubleshoot).

Suggested experiment order: (1) collect job/step timing and logs, (2) verify whether checkout, dependency install, cache transfer, action/tool downloads, test execution, or artifact upload dominates, (3) change one lever at a time, (4) compare median and tail time across warm and cold runs. Where a step invokes a package registry, that traffic is outside GitHub's runner endpoint list and needs its own measurement. The order is an inference from the documented transfer paths.

## Guardrails on persistent reuse

Self-hosted runners do not guarantee a clean environment between jobs. GitHub warns that untrusted workflow code can persistently compromise one and recommends ephemeral runners for autoscaling; public-repository PRs are especially risky. Retaining a package store or tool cache on this Mac should therefore be limited to trusted workflow execution, with secrets and write credentials kept away from untrusted code. Do not treat worktree reuse or cache persistence as an isolation boundary. [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use); [self-hosted runner reference](https://docs.github.com/en/actions/reference/runners/self-hosted-runners).

The runner auto-updates by default. Disabling updates can avoid unexpected update time but creates maintenance work: GitHub requires updating within 30 days of a release, and critical updates can block job assignment immediately. This is not a routine speed optimization for one Mac. [Self-hosted runner reference](https://docs.github.com/en/actions/reference/runners/self-hosted-runners#runner-software-updates-on-self-hosted-runners).
