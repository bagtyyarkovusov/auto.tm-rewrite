> Noncanonical research, accessed 2026-10-03. This note resolves factual questions for [Compare telemetry SDK support, managed features and team costs](https://github.com/bagtyyarkovusov/auto.tm-rewrite/issues/603). It selects no vendor, changes no policy and authorizes no signup, spending or deployment.

Repository baseline is `8af7428301d72ac8e252db06448d7812f838499d`. Context7 IDs resolved and queried were `/getsentry/sentry-docs`, `/posthog/posthog.com` and `/websites/glitchtip`. Official vendor pages and documentation source repositories supplied details the Context7 excerpts omitted. Several documentation pages returned unsupported Markdown content to the web reader, so their official GitHub source was read instead. No SDK was installed and no hosted runtime was tested.

## What AutoTM has today

- API and worker configure Pino. The API assigns request IDs, logs 5xx exceptions and returns a consistent error body. API `/healthz` reports process/deploy identity; `/readyz` probes Postgres, Redis and MinIO. These are useful foundations for diagnostics. They do not establish centralized error grouping, continuous uptime monitoring or delivered alerts. See [API composition](../../apps/api/src/app.module.ts#L32), [request IDs](../../apps/api/src/main.ts#L36), [error filter](../../apps/api/src/common/error.filter.ts#L60), [health controller](../../apps/api/src/common/health.controller.ts#L23) and [worker composition](../../apps/worker/src/app.module.ts#L25).
- Mobile's [error boundary](../../apps/mobile/components/ErrorBoundary.tsx#L30) logs to `console.error` and provides a retry UI. It does not upload reports. No Sentry, PostHog or GlitchTip SDK initialization, collector, analytics event storage or metrics exporter was found across the application workspaces.
- Admin contains moderation, audit and inspection-demand reporting. Its [navigation](../../apps/admin/src/app/(admin)/components/AdminNav.tsx#L3) has no general analytics dashboard. [Inspection demand](../../apps/api/src/modules/reports/infrastructure/PrismaInspectionInterestRepository.ts#L52) is a real domain aggregate. Listing `viewCount` exists, but [listing detail](../../apps/api/src/modules/listings/application/GetListingDetail.ts#L62) only reads it and no increment path was found.
- [Server B Compose](../../infra/compose/docker-compose.serverb.yml#L10) declares Prometheus, Grafana, Loki and GlitchTip. [Prometheus configuration](../../infra/docker/observability/prometheus.yml#L5) targets an absent API `/metrics` endpoint. No log collector, alert rules or deployed monitoring evidence was found. Checked-in configuration is not proof of an active service.

The [mobile package](../../apps/mobile/package.json), [admin package](../../apps/admin/package.json), [web package](../../apps/web/package.json), [API package](../../apps/api/package.json) and [lockfile](../../pnpm-lock.yaml) establish the Expo 55, React Native 0.83, Next.js 16 and NestJS stack. Vendor support for those frameworks does not prove compatibility with AutoTM's exact versions, Hermes bundles, native plugins, Metro configuration or release builds.

## What the options can provide

### Native crashes and readable production stacks

Sentry's React Native SDK enables its native layer and native crash handling by default. Its Expo plugin documents native-build source-map and debug-symbol upload. Native crash verification requires a release build, not Expo Go or a web build. `release` must match uploaded artifacts; the SDK supports `environment` attribution. AutoTM must verify both Hermes JS stacks and the relevant iOS/Android native stacks rather than treating a captured test exception as complete coverage. Sources are [React Native options](https://github.com/getsentry/sentry-docs/blob/master/docs/platforms/react-native/common/configuration/options.mdx), [Expo artifact upload](https://github.com/getsentry/sentry-docs/blob/master/includes/react-native-expo-plugin-code-snippet.mdx) and [native crash test restrictions](https://github.com/getsentry/sentry-docs/blob/master/docs/platforms/react-native/common/manual-setup/playground.mdx).

PostHog is not JS-only. Its optional `@posthog/react-native-plugin` adds native crash capture. `nativeCrashes` covers iOS Objective-C/Mach/signal crashes, including C/C++, and Android Java/Kotlin crashes. Android C/C++ capture additionally uses `androidNdkCrashes`, requires Android 12/API 31 or later, `posthog-react-native` 4.78.0+ and plugin 2.12.0+. Android NDK reports arrive on the next launch from OS records. The reported app version and identity describe that launch, and the first enabled launch can collect older OS-held crashes. This is a concrete attribution caveat for release comparisons, not evidence of AutoTM runtime behavior. See [PostHog React Native documentation](https://github.com/PostHog/posthog.com/blob/master/contents/docs/libraries/react-native/index.mdx).

PostHog documents Hermes JS source maps, iOS dSYMs, Android ProGuard/R8 mappings and `.so` debug symbols. JS automatic debug-ID injection requires Expo 50+, and native symbols need a separate build upload. Expo 55 clears that documented minimum; it does not prove plugin compatibility. Source maps do not symbolicate native crashes. See [React Native source maps and native symbols](https://github.com/PostHog/posthog.com/blob/master/contents/docs/error-tracking/upload-source-maps/react-native.mdx).

GlitchTip's current [React Native guide](https://glitchtip.com/sdkdocs/react-native/) explicitly documents native crashes on both platforms and requires `autoSessionTracking: false` because sessions are unsupported. Its [CLI](https://glitchtip.com/documentation/cli/) documents source-map debug IDs and native dSYM/PDB/ELF uploads. This is stronger evidence than generic Sentry compatibility alone, but the reviewed guide does not establish tested Expo 55/Hermes/R8 combinations or parity with Sentry release-health features. Those remain unknown until tested against a pinned collector and SDK version.

### API, worker, web and team workflows

Sentry documents Next.js and NestJS integrations and Node capture. Its NestJS docs say errors caught by a custom filter are not captured automatically. AutoTM's catch-all filter therefore needs explicit integration if Sentry is chosen. Sentry also documents isolated scopes for BullMQ/background jobs, so unrelated job breadcrumbs do not leak into HTTP errors. See [NestJS setup](https://github.com/getsentry/sentry-docs/blob/master/docs/platforms/javascript/guides/nestjs/index.mdx), [custom-filter capture](https://github.com/getsentry/sentry-docs/blob/master/platform-includes/getting-started-capture-errors/javascript.nestjs.mdx) and [Next.js](https://docs.sentry.io/platforms/javascript/guides/nextjs/).

PostHog documents Next.js client/server capture and a NestJS interceptor that captures 5xx exceptions when enabled. It also supports manual exception capture in Node. Its issues can be assigned, grouped and resolved; alerts include issue-created/reopened notifications, spike detection, webhooks and trend emails. See [Next.js setup](https://posthog.com/docs/error-tracking/installation/nextjs), [NestJS capture](https://github.com/PostHog/posthog.com/blob/master/contents/docs/error-tracking/installation/nestjs.mdx), [Node SDK](https://posthog.com/docs/libraries/node) and [error alerts](https://github.com/PostHog/posthog.com/blob/master/contents/docs/error-tracking/alerts.mdx).

Neither SDK's automatic uncaught-error capture proves visibility into BullMQ failures that the queue catches. The prototype must exercise API-filter errors and handled job failures, classify retry versus terminal failure, and verify alerts actually reach the responsible teammate. GlitchTip supports project-team email and webhook alerts; its hosted service is not the current repository choice. First-party product analytics still requires an event contract whichever error collector is selected.

## Team costs, caps, retention and regions

Prices below are USD, checked 2026-10-03. They exclude tax, replay, AI, tracing/log usage and additional access packages. No AutoTM event-volume estimate exists, so these are allowances and base prices, not a forecast.

| Option | Verified base cost and team access | Usage and retention |
|---|---|---|
| Sentry Developer | Free, one user | 5,000 errors/month; errors retained 30 days. Suitable for a single login, not independent teammate access. |
| Sentry Team | $26/month equivalent when billed annually, $312/year; unlimited users | 50,000 errors/month; errors retained 90 days. Additional ingestion is usage-priced. Current month-to-month checkout price was not independently verified. |
| Sentry Business | $80/month equivalent when billed annually, $960/year; unlimited users | 50,000 errors/month; errors retained 90 days. Extra features and usage are separately priced. Current month-to-month checkout price was not independently verified. |
| PostHog Cloud | Free tier has unlimited team members and one project; pay-as-you-go has six projects | 1 million analytics events and 100,000 exceptions/month free. Event retention is one year free and seven years paid. Usage above allowances is separately priced by product. |
| GlitchTip plus first-party analytics | No mandatory self-hosted per-seat subscription identified; hosting, storage and staff time remain AutoTM's costs | Self-hosted GlitchTip defaults to 90-day retention and permits configuration. First-party retention/aggregation must be built. The cost of that work has not been measured. |

Sources are [Sentry pricing](https://sentry.io/pricing/), [Sentry retention by data type](https://github.com/getsentry/sentry-docs/blob/master/docs/security-legal-pii/security/data-retention-periods.mdx), [PostHog pricing](https://posthog.com/pricing) and [GlitchTip self-hosting/retention configuration](https://glitchtip.com/documentation/install/). Sentry plus PostHog therefore has a verified team-access floor of $312/year on Sentry annual Team while PostHog stays within its free allowances. This is not the total operating cost.

PostHog Error Tracking documents a starting overage rate of $0.00037/exception. Its current product-analytics start guide says $0.000015/event, while its public landing page still says $0.00005/event. The marginal analytics rate is unresolved here; obtain the selected product's current calculator/checkout quote before budgeting. See [Error Tracking pricing](https://posthog.com/docs/error-tracking/start-here), [analytics start guide source](https://github.com/PostHog/posthog.com/blob/master/contents/docs/product-analytics/start-here.mdx) and [public landing page](https://posthog.com/).

Budget caps trade cost protection for missing data. PostHog permanently drops additional events at free-tier or billing limits. Sentry likewise does not retain over-quota events for later recovery; increasing quota starts accepting new events. Treat a cap as a potential diagnostics blind spot and verify usage alerts. See [PostHog cap behavior](https://posthog.com/pricing) and [Sentry dropped-event policy](https://www.sentry.help/en/articles/13964874-i-added-quota-why-can-i-not-see-my-dropped-events).

Sentry offers US/Iowa and EU/Frankfurt event storage. Some organization/account/integration metadata can remain in the US even with EU event storage. PostHog lists US/Virginia and EU/Frankfurt. Both are foreign destinations for TM production. Region selection does not settle regulatory suitability. Sources are [Sentry region facts](https://www.sentry.help/en/articles/13964378-sentry-s-eu-region-faq) and [PostHog pricing/region selector](https://posthog.com/pricing).

PostHog's [retention documentation](https://github.com/PostHog/posthog.com/blob/master/contents/docs/data/events-retention.mdx) says shorter rolling event retention is unavailable on request. Person/project/organization deletion is separate. Its standard retention differs from AutoTM's [90-180-day raw-event target](../prd/ops/85-launch-analytics-plan.md). That difference needs a human decision; a long query window is not evidence of a matching deletion policy.

## Privacy and delivery constraints

Sentry exposes `sendDefaultPii`, `beforeSend`, breadcrumb controls and separate screenshot/view-hierarchy/native-memory options. Disabling default PII does not prove secrets cannot occur in exception messages, URLs or custom context. PostHog exposes `before_send`, capture controls and explicit events. Adding its optional native plugin can also enable default push-subscription and push-open capture, so those settings need review. Sources are [Sentry RN options](https://github.com/getsentry/sentry-docs/blob/master/docs/platforms/react-native/common/configuration/options.mdx) and [PostHog RN options](https://github.com/PostHog/posthog.com/blob/master/contents/docs/libraries/react-native/index.mdx).

A useful starting constraint for a prototype is an allowlist of release, environment, service, error classification and approved product-event properties. Exclude codes, tokens, sign-in destinations, message content, raw GPS and full request bodies. Verify actual JS and native outbound payloads. Whether a JS scrubbing callback intercepts every native crash payload before native transmission was not established in the reviewed documentation. Native SDK paths require separate verification. Consent/disclosure requirements and allowed identifiers remain human-owned; this note makes no legal conclusion.

Delivery is bounded and can lose data:

- Sentry RN defaults to 30 cached envelopes and evicts the oldest when that limit is exceeded. Sentry documents an optional browser offline transport, not a universal guarantee of durable capture across all processes. Capture uses background queues; flush/close waits must have deadlines. Exact native request deadlines and Node persistence defaults were not established for a chosen SDK version. See [RN cache options](https://github.com/getsentry/sentry-docs/blob/master/docs/platforms/react-native/common/configuration/options.mdx) and [browser offline transport](https://github.com/getsentry/sentry-docs/blob/master/docs/platforms/javascript/common/best-practices/offline-caching.mdx).
- PostHog RN documents persistent file storage, a 1,000-event default queue, oldest-event eviction, three fetch retries, a 3-second retry delay and 10-second request timeout. It flushes queued events while online and can resume after reopening. Node documents a 10,000-event queue and bounded retry/timeout options, and recommends shutdown flushing. Those defaults are not a measured overhead or delivery guarantee for AutoTM. See [RN delivery configuration](https://github.com/PostHog/posthog.com/blob/master/contents/docs/libraries/react-native/index.mdx) and [Node delivery configuration](https://posthog.com/docs/libraries/node).

Ordinary captures should not wait on telemetry network delivery in AutoTM's request or interaction path. This is a proposed integration constraint, not proof that SDK initialization, serialization, hooks or native plugins are free of latency. Test unavailable collectors, queue overflow, app restart, container shutdown and crashes. Offline buffering cannot bridge an indefinite foreign-network outage or recover events discarded by a provider cap.

## TM boundary and the next decision

[ADR-0005](../adr/0005-hosting.md) assumes foreign connectivity from TM is blocked or unreliable and selects local production/observability. [ADR-0039](../adr/0039-phased-cloud-first-hosting.md) permits Railway for reviewer/demo hosting and permanent non-TM staging; TM-serving production still cuts over locally. [ADR-0010](../adr/0010-testing-obs.md) selects GlitchTip. [ADR-0023](../adr/0023-first-party-product-analytics.md) selects first-party events and excludes third-party analytics SDKs. These are policy boundaries, not evidence of current endpoint reachability.

[AGENTS.md](../../AGENTS.md) requires an approved external-egress decision. [ADR-0055](../adr/0055-resend-sends-sign-in-codes-from-the-worker.md#tm-era) permits worker-to-Resend through a host-specific Proxy PC allowance, with direct sending contingent on a recorded probe. It does not create a general telemetry route or a route from customer phones/browsers through that PC. Adopting managed diagnostics does not itself approve direct client egress or a hosting change. Existing [legal requirements](../prd/ops/83-legal.md) and [rendered privacy text](../../apps/web/src/app/[locale]/legal/content.ts) contain no foreign telemetry-provider disclosure.

A concrete failure scenario follows from that assumption. A TM buyer can use the local marketplace, then crashes. Direct upload to a foreign collector fails while AutoTM's local API stays reachable. Direct product-event uploads fail too, so the dashboard undercounts precisely those customers. A working worker proxy does not fix the customer's connection. Actual TM probes, any first-party intake/forwarding design and approved egress are still required.

Practical recommendation, as an inference: keep PostHog-only on the shortlist and verify it in a small release-build prototype before paying for two products. Its documented native support and free teammate access make that comparison worthwhile. If Android C/C++ crashes below API 31 must be covered, its documented native limit may rule it out as the sole collector. Sentry plus PostHog is a separate candidate when dedicated Sentry diagnostics are required. The existing local option remains the policy-aligned candidate when foreign telemetry cannot be relied on. None has runtime proof on AutoTM yet.

The founder still chooses the diagnostics coverage and supported OS matrix, product questions/events, release gates, responsible teammate/alert route, vendor or local ownership, region/retention/identifiers, budget and acceptable cap behavior, and TM ingestion/egress policy. This research does not resolve those choices. Exact SDK/build compatibility, native scrubbing, overhead, symbolication, alert receipt, TM connectivity and future monthly charges remain unverified.
