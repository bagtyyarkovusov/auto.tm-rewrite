03

What is wrong in the code today

The strongest new findings are at the joins between otherwise reasonable modules. I would fix these before spending time on broad refactoring. Three new isolated tests fail the guarantees we want, reproducing the problems with current source. This does not mean the existing repository suite is failing. No live database, API or object store was used. [20] [3]

P0 · reproduced with fake ports

A Listing's ownership does not prove ownership of its media object.

The caller must own the mutable parent Listing. But attachment accepts a supplied storage key without proving that the caller uploaded or owns that object. Public Listing detail exposes media keys. The media table permits repeated key references. Removing attached media then schedules deletion of the key's original and derivatives. [1]

The local test gives an attacker-owned Listing a key already referenced by a second Listing. Attachment accepts it; removal schedules cleanup under the second Listing's prefix. This confirms an application-level unauthorized deletion path. Real cloud deletion and a deployed HTTP attack were deliberately not attempted.

The repair must span upload, publish, attach and cleanup. Bind upload state to the User, validate provenance server-side, reject cross-user adoption and duplicate ownership, and delete only from authoritative ownership/reference state. Presigning currently generates a random pending key without preserving User ownership, and publication also trusts draft keys. Merely hiding keys or checking a caller-supplied prefix would leave the underlying gap. [21]

Start with a two-user negative test and legitimate-owner test, then cover retries and races. Historical #91 checked parent ownership; it did not establish uploaded-object ownership. Targeted issue search found no obvious open fix, but that is not proof that none exists under another title.

P1 · reproduced at the API boundary

Edit-save sends a local media ID where the server requires its own ID.

The mobile save hook attaches a new photo but ignores the returned server media ID. Reorder later uses the staging photo's local UUID. The server generated a different UUID, and the database updates by that server ID. The result can be a partly saved Listing followed by failed ordering. A retry with the same local UUID does not repair the mismatch. [5]

The existing test already mocks a distinct returned ID, but its reorder mock always succeeds. It checks the sequence of operations without checking whether the next service can accept the data. The new assertion expects the returned server ID and fails with the local one. This is the clearest testing lesson in the audit.

Keep a stable local-to-server ID map and save operation plan across retries. Test the actual reorder payload and final server state. Preserve the approved sequential best-effort save design; a large transactional API redesign is unnecessary for this correction. [22]

P1 · reproduced through the rendered route

Background refetch can reset dirty edit state.

The edit route dispatches INIT whenever its Listing query returns a new object. INIT replaces the payload and resets the wizard step. Edit, attach and remove mutations invalidate that same detail query while save work is still underway. [6]

The temporary route test selects an unsaved Damaged answer, then supplies a new Listing object that changes only favoriteCount. The answer is selected before the refresh and absent afterwards. That proves the state reset in React. Device timing and an actual network save were not tested.

Initialize an edit session once and keep its dirty draft separate from query snapshots. Reconcile after successful save or an explicit reload choice. Include a refetch during dirty edits and after one operation succeeds while a later operation fails.

P1 · source-confirmed, already ticketed

Account restoration happens before the user confirms.

Current VerifyOtp calls RecoverAccount during successful sign-in if deletion is scheduled. RecoverAccount clears that schedule and republishes affected Listings. The mobile screen subsequently shows Restore or Cancel; Cancel only clears local pending state. The October 2 prototype review reported this, and direct source inspection corroborates it. [23]

Finish existing issue #518 instead of opening a competing fix. Confirm should perform restoration; Cancel must preserve deletion state and Listing visibility. Cover phone, email and reviewer paths as applicable. This report adds no new runtime reproduction for that issue. [7]

What this says about the repo

The architecture is sound enough to isolate these failures and write meaningful tests. The weakness is joined behavior: identity, media IDs, storage ownership, caches and lifecycle state. A test suite can be large and still miss an assumption that two modules share.

04

Improve the quality of evidence

The source inventory counted 1,191 handwritten production/test files and about 137,000 lines across the apps and packages. The API has 167 test files and mobile 169. This is substantial software, not a small throwaway demo. The counts describe scale, not coverage or correctness. [20]

Fifty-one mobile test files read source text in some way, about 30% of the 169. Some mix useful behavioral and structural assertions; route and configuration checks can legitimately inspect source. The risk is treating text presence as proof that a person can see, press, retry or navigate something. The repo has already started migrating toward rendered behavior tests. Continue that work where regressions justify it.

The native adapter explicitly cannot prove layout, NativeWind resolution, keyboard behavior, native services, screen-reader output or real navigation. Those limitations are honest and useful. A passing rendered test must stay a narrower claim than a passing Android journey. [9]
