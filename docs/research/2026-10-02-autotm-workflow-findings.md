# AutoTM workflow and management audit

Audit date: 2026-10-02, Asia/Shanghai. Repository checkout at `8ed5dcb`, with read-only live GitHub observations taken during the audit. The project is actively changing, so issue/PR counts are a snapshot rather than a stable inventory. I read the root policy and context map, current issue/queue execution contracts, roadmap, sprint retros, relevant workflow ADRs, the September 29 workflow audit, and live issue/PR/protection/check metadata. I did not read private conversation history in this subtask, change repository files, create issues, or alter settings.

## Judgment

The repository's biggest workflow problem is now keeping delivery focused while its process catches up with rapid changes. It is not lacking instructions. In the last nine days, AutoTM adopted portable PR state, lighter small-fix reviews, shorter context, a single queue workflow, hosted CI, Railway PR native backends, and executable cleanup. Those were sensible corrections to real failures. Recommending them again would waste the founder's attention.

The next improvement should be a bounded operating experiment: finish the small known workflow debt, stabilize known CI faults, and run the current launch-critical queue for two weeks with measured outcomes. Avoid another broad workflow redesign during that experiment. This is a recommendation, not a new repository rule.

## What is already repaired

The repo has learned from its own failures. Keep these changes long enough to evaluate them.

- Durable Git/GitHub state now replaces chat-dependent handoffs. A reservation branch, early draft PR, checkpoint commits, and one mutable Execution state allow another client to resume. [ADR-0058](https://github.com/bagtyyarkovusov/auto.tm-rewrite/blob/8ed5dcbdd2ecbca3e494f4e18e17edd91f3c0edb/docs/adr/0058-portable-coding-agent-issue-execution-and-pull-request-gates.md#L21), [current state contract](https://github.com/bagtyyarkovusov/auto.tm-rewrite/blob/8ed5dcbdd2ecbca3e494f4e18e17edd91f3c0edb/.claude/skills/run-issue/EXECUTION-STATE.md#L3).
- Task-scoped context replaced 16,514 words of previously required common startup reading and an 8,539-word mobile overview. These are historical audit figures, not today's mandatory read size. Source and tests now own implementation facts. [ADR-0060](https://github.com/bagtyyarkovusov/auto.tm-rewrite/blob/8ed5dcbdd2ecbca3e494f4e18e17edd91f3c0edb/docs/adr/0060-source-first-agent-context-and-task-scoped-guidance.md#L12).
- Small changes gained a useful lighter route. The trigger was seven follow-up issues from two PRs, several only a few lines. Delta review and batching solve that specific cost. [ADR-0065](https://github.com/bagtyyarkovusov/auto.tm-rewrite/blob/8ed5dcbdd2ecbca3e494f4e18e17edd91f3c0edb/docs/adr/0065-small-changes-skip-the-issue-ceremony.md#L12).
- Fixed vendor assignments and manual review waivers were removed. Fresh read-only context, exact commit, and the review axis remain the contract. [ADR-0064](https://github.com/bagtyyarkovusov/auto.tm-rewrite/blob/8ed5dcbdd2ecbca3e494f4e18e17edd91f3c0edb/docs/adr/0064-any-supported-client-may-review-either-axis-and-issues-have-no-concurrency-limit.md#L12).

## Priority actions

### First, make one visible launch finish line

Keep #320 as the release map and #270 as the deployment sprint, with explicit links between them. Give the founder one short ordered queue and a separate human-action list. The queue should state which issues unblock physical Android proof #345 and signed release freeze #329. Show the next blocker and the next human action, rather than requiring the founder to reconstruct them across chats.

The Google Play window through October 12 is real in the roadmap, but #282 retains both-platform acceptance criteria and a founder hold. Do not silently mark it complete under an Android reinterpretation. Choose an explicit disposition if the intended Android-only release path must move sooner. This audit does not authorize production or acceptance changes. [Roadmap sequencing](https://github.com/bagtyyarkovusov/auto.tm-rewrite/blob/8ed5dcbdd2ecbca3e494f4e18e17edd91f3c0edb/docs/prd/03-roadmap.md#L43), [S11 hold](https://github.com/bagtyyarkovusov/auto.tm-rewrite/blob/8ed5dcbdd2ecbca3e494f4e18e17edd91f3c0edb/docs/prd/sprints/sprint-11-railway-deployment-retro.md#L79), [Android map #320](https://github.com/bagtyyarkovusov/auto.tm-rewrite/issues/320).

Make a release boundary explicit. Approved essential journeys and store requirements can block the release. New cosmetic preferences, support features, and further reference-app parity should default to a later bet unless a concrete acceptance failure makes them necessary. The founder has authorized the redesign; this recommendation is about preventing the finish line from moving while its implementation runs.

Counterargument: coherent UI and honest auth/deletion states are part of being reviewable, not optional decoration. Correct. Freeze only after identifying those essentials. A freeze that ships broken trust or account deletion is false economy.

### Next, clear two known workflow debts

Finish #407's factual header/check-name work and reconcile #404 with Sandcastle's retirement. Then fix the current ticket-producing prompt/template that copied ADR-0019 and sandbox boilerplate into #516 through #526. The lean current template already exists at [issue-tracker.md](https://github.com/bagtyyarkovusov/auto.tm-rewrite/blob/8ed5dcbdd2ecbca3e494f4e18e17edd91f3c0edb/docs/agents/issue-tracker.md#L90). This does not need a new framework or a broad documentation sweep.

Counterargument: the old references are readable and agents can resolve supersession. True, but every agent spending time resolving the same known ambiguity is exactly the cost ADR-0060 intended to remove. New issues should demonstrate the adopted policy.

### Then, stabilize the CI causes in #494

Require direct cause evidence, not “it passed on rerun.” Check all API e2e queue connections use the isolated REDIS_URL. Decide whether reviewer audit persistence must precede successful authentication or whether the test should observe eventual persistence. Ensure package generation cannot rewrite files while lint reads them. These faults affect every queued PR, so their value is higher than one more local UI refinement.

Counterargument: CI currently passes enough to merge. That does not remove repeated diagnosis and review delay when unrelated PRs intermittently fail. However, today's legitimate lint failures should continue blocking merges.

### Run a two-week operating experiment

Use the existing roles and gates. Record a small comparable cohort of roughly 8–12 PRs across ordinary API work, mobile UI work, and a small fix. A small measurement table is sufficient; preserve release-relevant results in the issue or PR. Capture issue-to-merge elapsed time, time blocked on a founder decision, number of pushes/check runs, full versus Delta reviews, accepted review findings, CI failures by cause, native proof time, and defects discovered after merge.

Also record interruptions that resumed from the PR without chat history. This directly tests the portability claim. ADR-0058 specified an eight-issue handoff pilot and a retrospective with elapsed time, review cycles, CI failures, human interventions, and resumability. I found no comparable completed outcome table in the scoped repository research/evidence paths. Later ADRs changed the pilot's concurrency and vendor rules, so do not treat its old two-issue cap as current policy. [Original measurement proposal](https://github.com/bagtyyarkovusov/auto.tm-rewrite/blob/8ed5dcbdd2ecbca3e494f4e18e17edd91f3c0edb/docs/adr/0058-portable-coding-agent-issue-execution-and-pull-request-gates.md#L60), [September audit's measurement advice](https://github.com/bagtyyarkovusov/auto.tm-rewrite/blob/8ed5dcbdd2ecbca3e494f4e18e17edd91f3c0edb/docs/research/2026-09-29-agent-workflow-audit.md#L139).

Change one operating variable at a time. Do not simultaneously change reviewer count, reasoning effort, concurrency, and issue size, then credit the winning metric to all four. The repo already has precise host profiles. Use those as the starting point, and test changes against actual outcomes. [Queue model profile](https://github.com/bagtyyarkovusov/auto.tm-rewrite/blob/8ed5dcbdd2ecbca3e494f4e18e17edd91f3c0edb/docs/agents/queue-models.md#L5).

## Capacity recommendation for one founder and several subscriptions

Treat subscriptions as execution capacity and recovery options. They do not multiply the founder's design, release, or production decision capacity. Keep one integration coordinator, one durable PR record per issue, and independent reviewer contexts. Use another available client when an implementer stops, rather than restarting the issue or assigning permanent vendor ownership.

Do not automatically run four UI writers because four subscription sessions exist. The repository allows up to four Codex issue implementers, while it explicitly limits the Mac to one heavy install/build/test phase at a time. Those are different capacities. Parallelize independent API/contracts/docs work and waiting review/CI; serialize contested simulator/UI control and resource-heavy phases. A proposed starting point is two active writing lanes, with spare capacity for review, fixes, and interrupted-work recovery. This is a scheduling experiment, not a policy limit, and it respects ADR-0064's absence of a hard issue cap. [Concurrency guidance](https://github.com/bagtyyarkovusov/auto.tm-rewrite/blob/8ed5dcbdd2ecbca3e494f4e18e17edd91f3c0edb/docs/agents/queue-models.md#L14), [host limit](https://github.com/bagtyyarkovusov/auto.tm-rewrite/blob/8ed5dcbdd2ecbca3e494f4e18e17edd91f3c0edb/docs/adr/0075-railway-pr-backends-for-agent-native-sessions.md#L24).

Measure the founder's interventions and time, not just tokens or merged issue count. A cheap subscription is still expensive if it creates decisions faster than one person can resolve them. Do not assume an ideal model/vendor split from brand reputation; the repository currently permits either client to review either axis and records actual attribution.

## A remaining enforcement gap worth watching

Live main protection requires the pr check, applies to administrators, disallows force pushes/deletion, and requires linear history. Approval count is zero, strict up-to-date checks are false, and conversation resolution is not required. The two independent fixed-SHA review passes therefore remain an operational contract enforced by the integration agent, not a GitHub approving-review gate. This is partly deliberate because agents use the founder's account and cannot approve their own PRs. [#407 disposition](https://github.com/bagtyyarkovusov/auto.tm-rewrite/issues/407#issuecomment-5882282507).

The current procedure correctly warns that a push does not cancel auto-merge. Forgetting to disable auto-merge before a fix could merge an unreviewed new head as soon as CI passes. [Finalization](https://github.com/bagtyyarkovusov/auto.tm-rewrite/blob/8ed5dcbdd2ecbca3e494f4e18e17edd91f3c0edb/.claude/skills/run-issue/FINALIZATION.md#L77).

A later small merge-readiness validator could check current head SHA, both review records or valid Delta carry-forward, readiness, and CI before enabling auto-merge. Start read-only and measure whether it catches omissions. It cannot prove that a reviewer was intellectually independent, and it must not count arbitrary text as approval. If concurrent merges produce integration regressions, evaluate stricter base freshness or a merge queue with evidence. I found no demonstrated bypass or concurrent-merge defect in this scoped audit; these are prevention candidates, below the immediate launch and CI priorities.

## What I would preserve

Preserve the framework-free domain/application boundaries, real integration coverage, testable issue outcomes, explicit missing-evidence states, fixed-SHA independent review, and native/physical release proof. Retros caught concrete problems: schema/contracts drift in S1, false closure bookkeeping in S5, missing simulator proof in S6, and fragmented host evidence in S10. Those checks earned their place. The production trigger-copy incident is also a reason to preserve provider-side readback before mutation. It was recorded honestly as an unmet historical criterion, rather than rewritten into success. [S11 incident disposition](https://github.com/bagtyyarkovusov/auto.tm-rewrite/blob/8ed5dcbdd2ecbca3e494f4e18e17edd91f3c0edb/docs/prd/sprints/sprint-11-railway-deployment-retro.md#L11). The strongest overall next action is to put the current system under a launch-focused, measured run. Finish known debt, keep the scope stable, and prove the exact Android candidate. Another orchestration rewrite will not solve a pending founder decision, an unrun physical-device gate, or a release map whose finish line continues to grow.
