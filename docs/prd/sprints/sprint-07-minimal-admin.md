# Sprint 7 — Minimal admin + moderation

| | |
|---|---|
| **Status** | ⚪ Pending |
| **Phase** | 1 (MLP beta) |
| **Milestone** | M6 — Admins can keep beta safe |
| **Demo audience** | Internal admins |
| **Estimated time** | ~1 week |

## Goal

Give internal admins enough control to run a private beta safely: review reported listings/users, ban or restore obvious abuse, and see an audit trail.

This sprint intentionally does not build the full admin dashboard from the old roadmap: no dealership verification queue, no broadcast tool, no marketplace analytics dashboard, no SMS health UI, no catalog mega-editor, and no blog moderation.

## User capability (the demo line)

> "I log in as an admin, open the reports queue, review a reported listing, ban it with a reason, and see the action in the audit log."

## Bounded contexts touched

- **Primary**: `admin/` — content reports + audit log
- **Supporting**: `listings/` ban/unban; `identity/` user suspend; `conversations/` only if S6 is explicitly reshaped to expose report-from-thread

## Implementation slicing

S7 should be created as one parent GitHub issue plus child issues. Do not run it as one giant admin PR. Child issues may be adjusted when the sprint starts, but they should preserve these dependencies:

1. **Contracts first** — add admin/auth schemas, canonical error reasons, response DTOs, and OpenAPI generation before API/app consumers depend on them.
2. **DB + operator path before UI** — land Prisma migration/indexes, `TotpEnrollment`, `ContentReport`, suspension fields, `packages/db/scripts/promote-admin.ts`, package command, and deterministic bootstrap/sample-report fixtures before admin pages are wired.
3. **Admin auth before admin exposure** — harden `AdminGuard`, TOTP enrollment/verify/status, JWT `sid`, TOTP secret validation, cookie bridge, and server-action refresh before protected admin pages are reachable.
4. **Public report creation before admin queue actions** — make listing/user report creation and mobile entry points testable before building report review actions.
5. **Moderation actions with enforcement tests** — listing ban/unban and user suspend/unsuspend must include the public/owner/contact/message enforcement tests in the same child PR, not as cleanup.
6. **Admin app server actions owned explicitly** — cookie storage, refresh-on-401 retry, expired-TOTP redirect, `returnTo` validation, Origin validation, logout clearing, and no-token-leak rendering need their own test owner.
7. **End-to-end smoke last** — finish with one deterministic path: create report -> TOTP-elevated admin action -> audit row visible -> public enforcement visible.
8. **Docs gate per child** — every child PR that changes a domain invariant (Prisma field, route, port, use-case, event, app/package structure) updates the relevant `CONTEXT.md` in the same PR per ADR-0019. Only defer a `CONTEXT.md` update to a sprint-final wiring issue if that deferral is explicit in the child issue body.

## Acceptance criteria (DoD)

- [ ] `AdminGuard` is hardened so every AdminGuard-protected API requires authenticated user, `role = admin`, and current TOTP elevation
- [ ] `apps/api` remains bearer-token only; `JwtAuthGuard` does not read cookies in the MLP
- [ ] `apps/admin` stores admin access/refresh tokens in HTTP-only cookies (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`) with max age aligned to the API access-token and refresh/session lifetimes. Canonical production cookie names are `__Host-auto_tm_admin_access` and `__Host-auto_tm_admin_refresh` with no `Domain` when admin runs on its own host. Local dev may use unprefixed `auto_tm_admin_access` / `auto_tm_admin_refresh` only when the `__Host-` constraints cannot be satisfied.
- [ ] Browser client code never receives admin tokens. Only Next.js server actions / route handlers call `apps/api`, forwarding `Authorization: Bearer <accessToken>`. No admin React component calls `apps/api` directly from the browser in S7.
- [ ] Admin server actions / route handlers refresh once on API HTTP 401: use the refresh cookie, rotate cookies on success, retry the original API call once, and clear cookies + redirect to login if refresh fails. Refresh may restore bearer auth but never extends TOTP elevation.
- [ ] If a refreshed or otherwise valid access token receives HTTP 403 from `AdminGuard` because TOTP elevation expired, `apps/admin` redirects to TOTP verification with a validated `returnTo` path. `returnTo` accepts only relative internal admin paths; absolute URLs, protocol-relative URLs, and cross-host redirects are rejected.
- [ ] After OTP verification on the admin host, if the authenticated user is not `role = admin`, `apps/admin` clears admin cookies and shows generic "Admin access required" copy. It does not expose whether the phone belongs to a normal user beyond the failed admin-host access.
- [ ] S7 does not add a separate CSRF-token system. Admin mutations stay behind same-site server actions / route handlers; if implementation introduces a browser-posted public route handler, it must validate `Origin` against the configured admin origin. Do not fall back to `Referer`.
- [ ] Admin logout attempts API logout server-side using the refresh token, but clears both admin cookies locally even if API logout fails. Logout-all attempts the bearer-protected API logout-all endpoint and then clears both cookies locally even if revoke fails.
- [ ] Access JWTs include `sid` (Session id); `AdminGuard` uses it to load the current Session and verify `adminTotpExpiresAt > now`
- [ ] `Session.adminTotpExpiresAt` stores a 12-hour admin elevation window created by successful TOTP verification
- [ ] Refresh-token rotation preserves the same Session id and existing `adminTotpExpiresAt`; refresh never extends admin TOTP elevation
- [ ] Admin OTP verification creates the normal non-elevated Session first; S7 does not add a temporary challenge-token system
- [ ] TOTP enrollment/verification upgrades that same Session by setting `adminTotpExpiresAt`
- [ ] TOTP enrollment/verification routes are authenticated with the normal JWT session but are not protected by `AdminGuard`; they require `role = admin`, valid `sid`, and Session ownership
- [ ] Normal OTP/refresh response contracts stay unchanged; admin TOTP state lives behind separate authenticated endpoints
- [ ] S7 contract literals are centralized in `packages/contracts`, not scattered as ad hoc API/admin strings. This includes report reason values, content-report status values, admin audit action constants, and canonical `details.reason` values such as `REPORT_TARGET_NOT_REPORTABLE`, `SELF_REPORT_NOT_ALLOWED`, `TOTP_ALREADY_ENROLLED`, `REPORT_TARGET_MISMATCH`, `REPORT_ALREADY_RESOLVED`, `REPORT_TARGET_NOT_ACTIONABLE`, `MODERATION_TARGET_STATE_CONFLICT`, `ADMIN_TARGET_NOT_MODERATABLE`, and `SELF_MODERATION_NOT_ALLOWED`.
- [ ] `GET /api/v1/auth/admin/totp/status` returns `enrolled`, `elevated`, and `adminTotpExpiresAt?` for the current admin session. It never returns TOTP secret material, QR material, backup codes, or backup-code counts.
- [ ] `POST /api/v1/auth/admin/totp/enroll` returns only first-time QR/enrollment material for the current admin user/session. If the admin already has a verified enrollment, it returns HTTP 409 `CONFLICT` with `details.reason = "TOTP_ALREADY_ENROLLED"`. If the admin only has a pending unverified enrollment, it may replace the pending secret and return fresh QR material so the admin is not stuck after losing the first QR before verification.
- [ ] TOTP enrollment QR / otpauth URI uses issuer label `auto.tm Admin`
- [ ] `POST /api/v1/auth/admin/totp/verify` verifies a TOTP code, completes enrollment, returns `adminTotpExpiresAt` plus 10 backup codes exactly once, and sets `Session.adminTotpExpiresAt`. TOTP verification accepts the current 30-second step plus one adjacent step for small clock skew.
- [ ] After enrollment, `POST /api/v1/auth/admin/totp/verify` accepts either a TOTP code or one backup code for admin elevation. Later verification responses return `adminTotpExpiresAt` only; backup codes are returned only on first successful enrollment verification, never on later logins.
- [ ] TOTP/backup-code verification has explicit attempt throttling on top of the global API throttler: max 5 failed attempts per admin user/session per 10 minutes. Wrong TOTP and wrong backup code return the same generic failure; throttled attempts return the standard rate-limit error. Successful verification resets the failure counter.
- [ ] Backup-code consumption is atomic: a backup code is marked used only in the same transaction/path as a successful match. Failed TOTP/backup-code attempts emit structured API security logs, not moderation `AuditLog` rows. S7 does not add permanent lockout, account suspension, or self-service recovery for failed admin TOTP attempts.
- [ ] After successful TOTP elevation, `apps/admin` redirects to `/reports`; S7 does not build a `/dashboard` landing page
- [ ] If `AdminGuard` rejects a request because TOTP elevation expired, it returns HTTP 403. `apps/admin` sends the admin back to TOTP verification and preserves the intended destination for redirect after successful re-verification.
- [ ] S7 does not add a multi-tab heartbeat or polling session monitor. The first tab/server action/page load that hits expired TOTP redirects to verification; other tabs discover expiry on their next protected server action or route load.
- [ ] Admin login uses the existing OTP identity flow plus S7-owned TOTP enrollment/verification for admin elevation per ADR-0006
- [ ] `TotpEnrollment` persists admin TOTP metadata; its shared secret is encrypted and recoverable with an app-level `TOTP_SECRET_ENCRYPTION_KEY`, not hashed
- [ ] `TOTP_SECRET_ENCRYPTION_KEY` is a required 32-byte base64 value validated at API startup; API startup fails fast if it is missing or invalid. S7 does not support runtime key rotation. Rotation requires a post-MLP operator runbook that decrypts and re-encrypts existing `TotpEnrollment` rows.
- [ ] Backup codes are stored one-way hashed separately from the encrypted TOTP secret
- [ ] S7 exercises `User.role = admin`, so the TOTP flow ships before the admin dashboard is exposed to beta operators
- [ ] First admin is provisioned through the checked-in operator path: `docs/prd/ops/86-admin-bootstrap-runbook.md` + `packages/db/scripts/promote-admin.ts`; ad hoc SQL is break-glass only
- [ ] The admin bootstrap script requires `--phone` and `--reason`, supports optional `--dry-run`, promotes an existing OTP-verified user by phone to `role = admin`, writes an audit row with operator reason, and does not create users, create TOTP enrollment, set `adminTotpExpiresAt`, mint tokens, or bypass `AdminGuard`
- [ ] `ADMIN_BOOTSTRAP_PROMOTE` uses `actorId = null`, `targetType = "user"`, and `targetId = promotedUserId`. `details.reason` is required and follows the same internal admin-reason text rules as moderation actions; `details.before.role` / `details.after.role` record the role change, and no phone snapshot is stored in `AuditLog.details`. If the user is already `admin`, the command exits successfully as a no-op without writing another audit row; if no user matches the phone, it fails and writes no audit row.
- [ ] `role = admin` before TOTP is a pending admin assignment, not usable admin access
- [ ] No production admin-role user may reach AdminGuard-protected APIs until S7 hardens `AdminGuard`; pre-S7 admin JWTs remain test/dev-only
- [ ] Admin elevation is issued only after OTP and TOTP both succeed; bare `role = admin` JWT access is insufficient for any AdminGuard-protected route, including existing `/api/v1/admin/catalog/*`
- [ ] S7 hardens auth for existing catalog admin APIs but does not build `/catalog` UI in `apps/admin`. Beta-critical catalog corrections use existing protected API/operator tooling; a small UI can only ship if S8 explicitly shapes it.
- [ ] Backup codes are generated only after successful TOTP verification per ADR-0006, stored hashed, displayed once with copy-to-clipboard, and covered by an operator recovery runbook; no printable PDF, regeneration UI, or self-service recovery UI in the MLP
- [ ] S7 ships no admin demotion/deprovision UI and no moderation-based admin suspension. Mistaken or compromised admin access is handled through operator runbook/session revocation; a proper admin-account-management capability is post-MLP.
- [ ] S7 `ContentReport.targetType` supports `listing` and `user`; `message` is added only if S6 explicitly ships report-from-thread, and `blog_post` is post-MLP because blog moderation is out of scope
- [ ] `ContentReport.targetType` + `targetId` are polymorphic target references with no DB FK to listing/user. Create-report use-cases validate target existence through the owning context before insert; admin action use-cases validate the target again before acting. If a target later disappears, admin report detail shows target unavailable while preserving report history.
- [ ] S7 `ContentReport.reason` is a small enum: `spam`, `scam`, `misleading`, `wrong_category`, `harassment`, `other`. `wrong_category` is valid only for listing reports; `harassment` is valid for user reports. `details` is optional except when `reason = other`, where it is required; trim leading/trailing whitespace before validation/storage, reject blank-after-trim `other` details, preserve internal line breaks, and cap at 1000 chars after trim. Report details are plain text only: no Markdown/HTML support, no S7 PII scan, no translation, no profanity filter, and no moderation classifier.
- [ ] `POST /api/v1/listings/{id}/report` creates a listing report ticket
- [ ] `POST /api/v1/users/{id}/report` creates a user report ticket
- [ ] Mobile report entry points are limited to existing public surfaces in S7: active non-owner listing detail and visible non-self public user profile. There is no global report button, no report history/status surface, and no message-report entry point unless S6 is explicitly reshaped to ship report-from-thread.
- [ ] Public report routes keep the resource-shaped URLs above for client ergonomics, but their controllers/use-cases live in `admin/` because `ContentReport` is the moderation ticket. The controllers map route params to `targetType` + `targetId`.
- [ ] `admin/` validates report targets through `ListingsReadPort` / `IdentityReadPort`. `listings/` and `identity/` do not store reports, emit report-created events, or depend on moderation internals.
- [ ] If S7 emits a report-created event, it is `ContentReportCreated` from `admin/` after a new report row commits, with generic payload `{ reportId, targetType, targetId, reporterUserId, reason }`. Duplicate pending reuse emits no `ContentReportCreated`. S7 ships no in-process consumers for this event; future admin alerts/notification tooling consumes `ContentReportCreated`, not `ListingReported`.
- [ ] Report creation requires an authenticated, non-suspended user; anonymous users are prompted to log in and no anonymous `ContentReport` rows exist in S7. `ContentReport.reporterUserId` is required at creation time but nullable for retention after account deletion (`onDelete: SetNull` or equivalent).
- [ ] If an anonymous user taps Report, mobile uses the existing auth-on-action pattern: open login, then resume the report sheet if cheap in S7; otherwise return to the same target detail and require one more tap. S7 does not add a new auth challenge or anonymous report draft model for reporting.
- [ ] If a suspended user tries to submit a report, the API blocks it through the suspended-user mutation policy. Mobile shows a generic account-restricted state and does not add report-specific suspension copy.
- [ ] Report validity is based on creation-time reporter checks plus review-time target actionability. If the reporter is later suspended or deleted, existing reports remain pending/actionable/dismissible; deleted reporters render as "Deleted user," and suspended reporters do not auto-invalidate their earlier reports. S7 does not add reporter-trust scoring, abusive-reporter auto-invalidation, or retroactive report purge behavior.
- [ ] S7 does not add a report-specific per-user quota, quota table, or custom report throttling rule. Public report routes rely on the existing global API throttler, authenticated-only submission, suspended-user mutation block, self-report rejection, duplicate pending dedupe, and no auto-hide-on-report. If beta shows queue spam across many targets, shape a post-MLP moderation-abuse PRD with per-reporter quotas and reporting-rate analytics.
- [ ] S7 public report targets are intentionally narrow. Listing reports are accepted only for currently `active` listings. Missing, soft-deleted, draft, archived, banned, and other non-public listing targets return HTTP 404 with the standard `NOT_FOUND` envelope. Visible but non-reportable listing states, such as `sold`, return HTTP 400 `VALIDATION_FAILED` with `details.reason = "REPORT_TARGET_NOT_REPORTABLE"`.
- [ ] User reports are accepted only for existing, non-deleted users that are reachable through a public surface. Suspended users remain reportable only while the target is still visible/reachable. A visible `role = admin` user can be reported through the same public route; public report creation must not reveal or special-case staff role. Missing, deleted, or otherwise hidden user targets return HTTP 404 `NOT_FOUND`.
- [ ] S7 rejects self-reporting: a user cannot report their own profile, and a seller cannot report a listing they own. The API returns HTTP 400 with the standard `VALIDATION_FAILED` error envelope and `details.reason = "SELF_REPORT_NOT_ALLOWED"`. Admins use direct admin action pages for internal moderation instead of creating public reports against their own targets.
- [ ] `ContentReport.reviewedById` is also nullable for retention after admin account deletion. Deleted reporters/admin reviewers render as "Deleted user" in admin report detail; no reporter/admin phone/name snapshot is stored on `ContentReport` in the MLP.
- [ ] Duplicate report handling is application-level: if the same reporter reports the same target while a report is still `pending`, return HTTP 200 with the existing pending report instead of creating another row. New reports return HTTP 201. Both responses use the same body shape: `{ reportId, status, createdAt, reusedExisting }`, with `reusedExisting = false` for new rows and `true` for duplicate pending reuse. Duplicate reuse preserves the original `createdAt`, does not bump the report's queue position, and emits no report-created event. Different reporters can create separate pending reports for the same target. Once a report is `dismissed` or `actioned`, the same reporter may report the target again. S7 does not add a DB partial unique index for this.
- [ ] Creating listing reports does not change `Listing.status`, hide the listing, or remove it from public surfaces; report count alone never triggers automatic hiding in S7
- [ ] Report submission returns the same generic success state to the reporter for both new reports and duplicate pending reuse: "Thanks, we received your report." Mobile does not display report id, queue status, duplicate/reused state, reviewer state, or target staff role. The public DTO's only duplicate signal is `reusedExisting`; it must not include target summary, sibling report counts, reporter history counts, staff role, reviewer state, or admin notes.
- [ ] If the target becomes unavailable or non-reportable between screen load and submit, mobile maps `NOT_FOUND` / `REPORT_TARGET_NOT_REPORTABLE` to generic copy: "This item is no longer available to report."
- [ ] Report resolution is internal in S7: no push notification, no in-app feed item, no "report reviewed" message, and no admin free-text reason exposed to reporters, listing owners, suspended users, or public users. S7 public reporting is submit-only: reporters cannot view a report history, track report status, edit submitted report details, retract reports, or start appeals/support workflows through public API/mobile UI.
- [ ] `GET /api/v1/admin/reports?status=pending` lists report tickets with `OffsetPagination` (`page`, `pageSize`; default page size 50, S7 effective max page size 100), defaults `status=pending`, sorts by `createdAt ASC, id ASC` so oldest pending reports are handled first with deterministic ties, and supports only `status` + `targetType` filters in S7. List rows expose exactly the triage fields `id`, `status`, `createdAt`, `reason`, `targetType`, `targetId`, and `targetSummary`. `targetSummary` is live-resolved and presentation-safe: listing targets use a display title such as year/make/model or listing title when available; user targets use a public display label when available; missing targets use an unavailable/deleted marker such as `{ available: false, label: "Unavailable target" }` while preserving `targetType` + `targetId`. List rows stay lean and do not include report `details` preview text, reporter identity fields, full target state, counts, actionability flags, or user target role; full details, reporter summary, target state, counts, actionability, and role are fetched only on report detail.
- [ ] S7 summary DTOs are stable contract shapes, not loose strings. `targetSummary` always carries `available`, `label`, `targetType`, and `targetId`; unavailable targets use `available = false` plus label `"Unavailable target"`, while available targets use `available = true` and may add detail-only fields only on report detail. Audit `actorSummary` distinguishes authenticated deleted admins from operator scripts, so `actorId = null` for `ADMIN_BOOTSTRAP_PROMOTE` renders as operator-script provenance instead of a deleted admin.
- [ ] Invalid admin table filters or pagination (`status`, `targetType`, `action`, `targetId`, `page`, or `pageSize`) return HTTP 400 `VALIDATION_FAILED`. `apps/admin` resets invalid report-list filters to the default pending queue instead of preserving a broken URL state.
- [ ] Valid admin report/audit list pages beyond the current result set return HTTP 200 with an empty row array and normal pagination metadata; only invalid `page` / `pageSize` values return `VALIDATION_FAILED`.
- [ ] `GET /api/v1/admin/reports/{id}` shows lean S7 context only: reporter summary or deleted-user state, target summary or target-unavailable state, report reason/details, status/timestamps, target current moderation state, `reportsSubmittedByReporterCount` when reporter still exists, and `pendingReportsOnTargetCount`. Detail target summaries may include listing title/year/make/model/status and, for user targets, the admin-only `target.role` so the UI can explain/disable admin-target suspend; this role is never exposed by public report creation or report list rows. Reporter/reviewer summaries are live minimal identity summaries or deleted-user state; `ContentReport` stores no phone/name/profile snapshots. `pendingReportsOnTargetCount` counts currently pending reports for the same `targetType` + `targetId`, including the current report if it is still pending. `reportsSubmittedByReporterCount` counts all historical S7 `ContentReport` rows by that reporter across listing/user targets and all statuses; omit it when `reporterUserId` is null after deletion. These counts are computed live in `GetReportDetail`; S7 does not add denormalized count columns, counter tables, or client-side aggregate state for them. The API stores enum reason values and the admin UI maps human labels locally. Admin UI renders report details as escaped plain text, preserving line breaks; no Markdown, links, HTML, truncation contract, or rich preview ships in S7.
- [ ] S7 `ContentReport` query shape is intentionally narrow and indexed for the MLP: pending queue uses `(status, createdAt, id)`, target pending count/detail lookups use `(targetType, targetId, status)`, and reporter history count uses `(reporterUserId, createdAt, id)`. S7 does not add denormalized report-count columns, counter tables, partial unique indexes, or JSON/GIN indexes for report details.
- [ ] S7 report detail does not show rolling windows, trust scores, severity scores, conversation excerpts, deep reporter/owner history, reporter reputation, cross-report clustering, precomputed report-count read models, or moderation-intelligence signals; those are post-MLP candidates
- [ ] S7 admin moderation actions (`dismiss`, `ban`, `unban`, `suspend`, `unsuspend`) require an internal plain-text `reason`, trimmed before validation/storage, non-empty after trim, capped at 1000 chars after trim, with internal line breaks preserved. The normalized reason is stored in `AuditLog.details.reason`; suspend also copies it into `User.suspensionReason` as current internal state. Admin UI renders reasons as escaped plain text. S7 has no admin-reason enum, preset picker, templates, classifier, or public/owner-facing exposure of admin reasons.
- [ ] `POST /api/v1/admin/reports/{id}/dismiss` accepts only pending reports, sets `ContentReport.status = dismissed`, sets `reviewedById`/`reviewedAt`, records an audit entry with required reason, and does not mutate the target
- [ ] `POST /api/v1/admin/listings/{id}/ban` accepts only `active` listings, sets `Listing.status = banned` through `ListingsAdminPort.banActiveListing`, hides the listing from public surfaces, blocks new contact/new messages for that listing, and leaves existing conversation history readable. It accepts optional `reportId`; when present, the admin use-case verifies the pending report targets that listing and marks only that supplied report `actioned` in the same transaction as the ban and audit write. Other pending reports on the same listing remain pending for manual dismissal.
- [ ] Banned listings are omitted from public feed/search/favorites surfaces. Non-owner public detail reads return HTTP 404 `NOT_FOUND`. Owner-scoped surfaces may show the owner's banned listing with a generic banned notice, but no report metadata, admin reason, or reporter identity.
- [ ] Owner listing mutations against banned listings are blocked until admin unban: edit, media attach/remove/reorder, mark sold, archive, republish, and delete do not proceed through normal owner routes. S7 does not use owner delete/archive as a workaround for admin ban.
- [ ] `POST /api/v1/admin/listings/{id}/unban` accepts only `banned` listings and restores them to `active` through `ListingsAdminPort.unbanBannedListing`; S7 does not store or restore a `previousStatus`. Unban does not clear favorites, recreate saved-search notifications, or resolve/dismiss pending reports.
- [ ] `POST /api/v1/admin/users/{id}/suspend` accepts only currently unsuspended non-admin users, sets `suspendedAt`, `suspendedById`, and internal `suspensionReason` through `IdentityAdminPort.suspendUser`, and blocks abusive user actions. It accepts optional `reportId`; when present, the admin use-case verifies the pending report targets that user and marks only that supplied report `actioned` in the same transaction as the suspension and audit write. Other pending reports on the same user remain pending for manual dismissal.
- [ ] `POST /api/v1/admin/users/{id}/unsuspend` accepts only currently suspended non-admin users and clears `suspendedAt`, `suspendedById`, and `suspensionReason` through `IdentityAdminPort.unsuspendUser`
- [ ] Admin mutation endpoints return HTTP 200 with small JSON response bodies, not `204`. `DismissReport` returns `reportId`, `status = dismissed`, `reviewedAt`, and `auditLogId`. Report-backed ban/suspend returns target id/state, supplied `reportId`, `reportStatus = actioned`, and `auditLogId`, but no sibling report counts. Direct ban/suspend returns target id/state and `auditLogId` with no report fields. Unban/unsuspend return target id/state and `auditLogId`; their request schemas do not accept `reportId`.
- [ ] Every successful S7 admin moderation mutation that changes report, listing, or user moderation state must commit its matching `AuditLog` row in the same transaction/path. If the audit write fails, the whole mutation fails and rolls back; S7 never allows unaudited moderation state changes as a fallback.
- [ ] S7 moderation write transactions are owned by the `admin/` use-case. Report resolution, target mutation through `ListingsAdminPort` / `IdentityAdminPort`, and audit write run inside one Prisma transaction for report-backed ban/suspend and direct ban/unban/suspend/unsuspend. `listings/` and `identity/` keep ownership of target-state rules, but their S7 admin ports must participate in the caller's transaction or expose a transaction-scoped adapter; they must not open independent write transactions for these admin moderation calls.
- [ ] S7 moderation cannot suspend or unsuspend admins. User moderation rejects `role = admin` targets with HTTP 403 `FORBIDDEN` and `details.reason = "ADMIN_TARGET_NOT_MODERATABLE"`; attempts by an admin to suspend/unsuspend their own account return HTTP 403 `FORBIDDEN` with `details.reason = "SELF_MODERATION_NOT_ALLOWED"`. These policy failures write no audit row, mutate no user state, and do not resolve a supplied report. Admin account compromise/abuse is handled by operator runbook or post-MLP admin-account-management work, not the report queue.
- [ ] If a pending report targets a visible admin account, the report remains a normal `ContentReport`; admins can dismiss it, but report-backed suspend is forbidden by the admin-target rule above. S7 does not add public staff-role leakage, special public admin-report errors, or automatic staff-abuse workflows.
- [ ] Report-backed ban/suspend validates the supplied `reportId` before any target mutation or audit write. Unknown referenced reports return HTTP 404 `NOT_FOUND`. Existing reports whose `targetType`/`targetId` do not match the route target return HTTP 400 `VALIDATION_FAILED` with `details.reason = "REPORT_TARGET_MISMATCH"`. Matching but already-resolved reports return HTTP 409 `CONFLICT` with `details.reason = "REPORT_ALREADY_RESOLVED"`. Matching pending reports whose target is no longer actionable return `REPORT_TARGET_NOT_ACTIONABLE` as below.
- [ ] Direct moderation actions revalidate current target state at write time. Missing/deleted targets return HTTP 404 `NOT_FOUND`. Existing targets in the wrong state return HTTP 409 `CONFLICT` with `details.reason = "MODERATION_TARGET_STATE_CONFLICT"` and current target state when known. Failed state-conflict requests write no audit row and perform no mutation. Admin UI hides or disables impossible actions when current state is known, but still handles this 409 because state can change after page load.
- [ ] Pending reports remain dismissible even if the target later disappears or changes state. Actioning a pending report revalidates current target state: ban requires the listing still exists and is `active`; suspend requires the user still exists, is not deleted, and is not already suspended. If the report is still pending but its target is no longer actionable, return HTTP 409 `CONFLICT` with `details.reason = "REPORT_TARGET_NOT_ACTIONABLE"` and include current target state when known. The failed action writes no audit row, does not mutate the target, and leaves the report pending for dismissal or refresh.
- [ ] Pending reports do not freeze target lifecycle in S7. Listing owners can still archive/delete their listings through normal listing flows, and users can still delete their accounts through the identity deletion flow even when pending reports exist. If the target disappears or becomes non-actionable before admin review, the report remains visible with target unavailable, dismiss remains available, and report-backed ban/suspend returns `REPORT_TARGET_NOT_ACTIONABLE`. S7 adds no target-lock, moderation-hold, or legal-hold behavior.
- [ ] Report-backed actionability is current-state only. A still-pending report is not invalidated by an earlier direct ban/unban or suspend/unsuspend cycle; if the target is currently actionable at review time, the report can be actioned. S7 does not add moderation epochs, report invalidation snapshots, or staleness-lock fields for this.
- [ ] Pending reports do not expire or auto-dismiss in S7. A report remains `pending` until an admin dismisses it or actions the supplied matching report through ban/suspend. S7 does not add age-based report state, SLA timers, scheduled cleanup jobs, or auto-close behavior; age filters, escalation, and auto-close belong in post-MLP moderation-operations/dashboard work if queue volume requires them.
- [ ] User suspension is stored directly on `User` and mutated only by `identity/`; `admin/` orchestrates report resolution/audit and calls `IdentityAdminPort`. Full who/why/history lives in `AuditLog`, not a separate `UserSuspension` entity. `User.suspensionReason` is an internal current-state reason copied from the normalized admin action reason. S7 does not ship suspension durations, automatic expiry, warning ladders, or a separate suspension-history table.
- [ ] Suspended users may still log in, log out, browse public surfaces, view the suspension state, and delete their account; they cannot create/edit/publish listings, contact/message sellers, submit reports, or perform other authenticated marketplace mutations. Blocked authenticated mutations return HTTP 403 `FORBIDDEN` with `details.reason = "USER_SUSPENDED"` and generic client copy.
- [ ] User suspension does not auto-ban, hide, archive, or delete the user's listings. Listing visibility remains governed by listing status/admin bans; admins ban listings separately when needed.
- [ ] If either conversation participant is suspended, new contact/message sends are blocked with the same suspended-user policy, but existing conversation history remains readable.
- [ ] Reported listing owners and reported users do not see report metadata in S7: no report count, report reason/details, reporter identity, report status, or admin notes. If a listing is banned or a user is suspended, they see generic state notices only. S7 does not ship appeals, owner-facing reason templates, or notification-copy workflows for moderation outcomes.
- [ ] Every admin action writes an `AuditLog` row with actor, target, action, internal reason, timestamp
- [ ] Audit targets follow the thing actually mutated. `CONTENT_REPORT_RESOLVE` for dismiss uses `targetType = "content_report"` and `targetId = reportId`; `AuditLog.details.reportedTargetType` and `details.reportedTargetId` preserve the listing/user the report was about. Report-backed `LISTING_BAN` / `USER_SUSPEND` rows target the moderated entity (`targetType = "listing"` or `"user"`, `targetId = actual target id`) and carry `details.reportId`.
- [ ] `AuditLog.details.before` / `details.after` stay minimal and structured in S7: dismiss records report status before/after; report-backed ban/suspend records the supplied report status before/after plus listing status or user suspension fields before/after; direct ban/unban records listing status before/after; direct suspend/unsuspend records user suspension fields before/after. S7 does not add a first-class before/after diff UI.
- [ ] S7 has no report assignment/claim workflow. Every report resolution conditionally updates only `ContentReport.status = pending`; concurrent resolution attempts never overwrite `reviewedById`/`reviewedAt`.
- [ ] If a report was already resolved by another admin, the API returns HTTP 409 using the standard `CONFLICT` error envelope with `details.reason = "REPORT_ALREADY_RESOLVED"` and the current report status. No audit row or target mutation is written for the losing request.
- [ ] For ban/suspend with a matching pending `reportId`, the supplied report's status update, target mutation, and audit write are one transaction: all succeed or all roll back. Failed report-backed validation (`NOT_FOUND`, `REPORT_TARGET_MISMATCH`, `REPORT_ALREADY_RESOLVED`, `REPORT_TARGET_NOT_ACTIONABLE`) writes no audit row and performs no target mutation. S7 does not cascade `actioned` or `dismissed` to sibling pending reports on the same target. Direct ban/suspend without `reportId` remains allowed and does not touch reports, even when pending reports already exist for that target.
- [ ] Report-backed moderation performs write-time revalidation inside the transaction: the supplied report must still be pending and matched to the route target, and the target must still be in the required current state. Concurrent attempts resolve exactly one request; the losing request rolls back with `REPORT_ALREADY_RESOLVED`, `REPORT_TARGET_NOT_ACTIONABLE`, or `MODERATION_TARGET_STATE_CONFLICT` and writes no audit row.
- [ ] S7 does not add idempotency keys for admin moderation mutations. Double submits rely on current-state validation: if the first request succeeds, the second returns `REPORT_ALREADY_RESOLVED` for the same report or `MODERATION_TARGET_STATE_CONFLICT` for the changed target state.
- [ ] Bad moderation decisions are reversed through normal admin actions, not audit edits. A mistaken listing ban is corrected with `unban`; a mistaken user suspension is corrected with `unsuspend`; both require a new internal reason and write a new audit row. Audit rows remain append-only and are never deleted, patched, or rewritten to hide the original decision.
- [ ] Successful moderation state changes may emit internal domain events only after the outer moderation transaction commits: `ListingBanned` / `ListingUnbanned` from `listings/`, `UserSuspended` / `UserUnsuspended` from `identity/`, and `AuditEntryRecorded` from `admin/`. S7 has no user-facing event consumers, so post-commit event publication failure is logged/observable but does not create a compensating moderation rollback.
- [ ] S7 moderation events have no user-facing consumers: no push, no in-app feed item, no conversation auto-close, no conversation system message, no owner notification, and no reporter notification. Conversations, notifications, and workers may consume these events only in a later sprint with explicit PRD coverage.
- [ ] S7 enforcement comes from synchronous state checks, not event side effects: listing status blocks new contact/messages, and `User.suspendedAt` blocks authenticated marketplace mutations.
- [ ] S7 keeps `AuditLog.action` as a String and does not add a Prisma enum/backfill migration. Canonical action constants live in code/contracts. `AuditLog.details` carries structured metadata (`reason`, `reportId?`, `reportedTargetType?`, `reportedTargetId?`, `before?`, `after?`, action-specific fields); `details.reason` is normalized internal plain text, not rich text. S7 does not add `beforeJson`, `afterJson`, or a top-level `reason` column unless implementation proves `details` is insufficient.
- [ ] `GET /api/v1/admin/audit` lists audit rows with `OffsetPagination` (`page`, `pageSize`; default page size 50, S7 effective max page size 100), defaults to `createdAt DESC, id DESC` for deterministic ties, and supports only `action`, `targetType`, and `targetId` filters in S7. List rows expose `id`, `createdAt`, `action`, `actorSummary`, `targetType`, `targetId`, a short target label, and optionally a one-line escaped plain-text reason preview. They do not expose full `details` JSON in the table. Deleted/null actors render as "Deleted admin" for normal admin actions and "Operator script" for `ADMIN_BOOTSTRAP_PROMOTE`. Missing/deleted targets keep the audit row visible and render "Unavailable target"; the audit list never fails because the current listing/user/report target disappeared. Full audit detail can be an inline expand row or side panel when needed; S7 does not require a dedicated audit detail page. CSV export, retention controls, full-text search, actor/date-range filter UI, and polished before/after diff are post-MLP dashboard work. S7 audit rows are append-only and retained indefinitely for the MLP.
- [ ] S7 audit-list query shape is indexed for the MLP: default newest-first list uses `(createdAt, id)`, action-filtered list uses `(action, createdAt, id)`, and target-filtered list uses `(targetType, targetId, createdAt, id)`. S7 does not query/filter `AuditLog.details` JSON, so it does not add a JSON/GIN index for audit details.
- [ ] Direct ban/suspend without `reportId` is allowed and does not touch any `ContentReport`; pending reports on that target remain pending for manual dismissal. S7 does not add a separate "action report" endpoint.
- [ ] Admin UI does not compute or warn with pending-report counts before direct ban/suspend in S7. On successful dismiss/ban/suspend/unban/unsuspend, it refreshes the current report detail/list or action page from the server response and does not locally rebalance paginated report pages. On failed mutation, it discards optimistic state and refreshes the report detail or action page.
- [ ] `/listings/:id` and `/users/:id` in `apps/admin` are narrow deep-link action pages for known targets. S7 does not ship `/listings` or `/users` admin index/search pages; full listing/user browsing is post-MLP dashboard work.
- [ ] Unban/unsuspend discoverability in S7 is acceptable through known target id, report-detail links, or audit-log target links only. S7 does not ship "banned listings" or "suspended users" queues; those are post-MLP dashboard filters.
- [ ] Admin moderation confirmation modals use static action-specific impact copy, not computed aggregate counts. S7 does not query "affected listings/conversations" for confirmation because suspend does not auto-ban listings and ban does not close existing conversations.
- [ ] Minimal `apps/admin` UI includes reports list, report detail, listing/user action forms, and audit log list. The pending reports queue has a simple empty state for `status=pending`; no dashboard cards or analytics are required.
- [ ] Private beta cannot start until S7 has an operator-visible launch-safety path: report entry can be paused with `REPORT_ENTRY_ENABLED=false`, admin moderation writes can be paused with `ADMIN_MODERATION_ACTIONS_ENABLED=false`, public browsing plus admin report/audit reads remain available where possible, and the deterministic report -> TOTP admin action -> audit -> public enforcement smoke passes in a prod-like environment. These are server-side environment/deployment config flags for the MLP; API enforcement is authoritative, UI hiding/disabled states are secondary. Disabled feature writes return HTTP 403 `FORBIDDEN` with `details.reason = "FEATURE_DISABLED"` and do not expose internal flag names.
- [ ] All S7 contract date/time fields (`createdAt`, `reviewedAt`, `adminTotpExpiresAt`, audit timestamps, error timestamps, and mutation response timestamps) are ISO-8601 strings validated with the existing contracts datetime convention. API/admin/mobile code must not exchange raw `Date` objects or locale-formatted date strings.
