# ADR-0029: Self-hosted Expo Updates (OTA) + hybrid air-gapped app delivery

- **Status**: Accepted
- **Date**: 2026-06-07
- **Deciders**: AutoTM founder + AI architect

## Context

AutoTM ships an Expo SDK 55 mobile app (ADR-0011) into an air-gapped Turkmenistan deployment (ADR-0005): TM hosts cannot reach abroad except FCM/APNS, and real users are inside TM on Telecom.

Two default delivery mechanisms both depend on servers abroad that TM throttles or blocks:

- **Over-the-air updates.** Expo's default EAS Update serves manifests and bundles from Expo's cloud CDN (abroad). Unreliable or unreachable from TM at runtime.
- **Binary install.** The App Store and Google Play deliver binaries from Apple/Google CDNs (abroad), which are intermittently throttled in TM; direct-APK sideloading is the cultural norm.

We want fast iteration during the private beta (ADR-0027 / S8) and after public launch — without re-submitting a binary for every JavaScript change. The production backend `api.auto.tm` is reachable from abroad (inbound-open, outbound-blocked), so reviewers and TM diaspora can use the app; but that does not help abroad-hosted update/binary CDNs reach users on Telecom.

The Expo Updates protocol can be self-hosted: the client app's `updates.url` points at any server implementing the protocol, with code-signed manifests (verified via Context7 against `/expo/custom-expo-updates-server`). This matches the existing self-hosted-everything posture (MinIO, ffmpeg, observability all run inside TM).

## Decision

**OTA updates are self-hosted inside Turkmenistan, and app-binary delivery is hybrid (store tracks + direct-APK fallback).**

- **Self-hosted OTA.** The mobile app's `updates.url` points at a first-party Expo Updates server on TM infrastructure (`updates.auto.tm`). Update bundles are stored in the existing self-hosted MinIO; manifests are code-signed with keys generated by `@expo/code-signing-certificates` (private key server-side in TM, public certificate embedded in the build). There is no runtime dependency on EAS Update cloud.
- **Hybrid binary delivery.** Initial install is via store tracks (Google Play closed/internal testing, Apple TestFlight) for legitimacy and the eventual public path, with **direct-APK download as the TM fallback** — and the primary Android path if Play is throttled on Telecom. Binaries are built with EAS Build (cloud, abroad) or locally; building is not air-gapped because CI/dev machines are outside TM (charter §9). Only the runtime backend is air-gapped.
- **OTA is JS/assets only.** Native changes (new native modules, SDK upgrades, new permissions, the deferred video pipeline) require a fresh binary and a bumped `runtimeVersion`; they are never shipped over OTA.
- **Channel discipline.** Beta cohorts are pinned to a stable OTA channel; parallel/dev work uses a separate channel and is never pushed to the beta channel mid-test.

## Consequences

### Positive

- TM users receive updates with no abroad dependency — consistent with the self-hosted-everything posture (MinIO, ffmpeg, observability).
- Fast iteration during and after beta: JS/asset fixes ship over-the-air with no store re-review.
- Resilient to Play Store / Expo-cloud throttling in TM via the direct-APK fallback.
- Reuses existing infrastructure (MinIO for bundles, Caddy for TLS, Node for the service) — the update server is a thin addition.

### Negative / accepted costs

- We own and operate the update server, code-signing key custody, and `runtimeVersion` discipline. A signing-key leak or a runtimeVersion mismatch can break or brick OTA delivery.
- EAS Update conveniences (hosted dashboard, staged rollouts, channel UI) are not available; any equivalent is built minimally in-house.
- Hybrid delivery means two binary-distribution paths (store builds + APK) to keep in sync.
- Native-change releases still require the slow path (rebuild + redistribute), so not all iteration is fast.

### Neutral

- Building on EAS Build (abroad) remains allowed; it does not violate the air-gap because builds do not run in TM.
- The public store launch (post-beta) still uses Play/App Store for binary distribution; self-hosted OTA layers on top via `updates.url`.
- A new `updates.auto.tm` service and its CONTEXT.md are added when the server actually ships (per ADR-0019), not before.

## Alternatives considered

- **EAS Update cloud (Expo default).** Rejected: serves bundles from abroad; unreliable or blocked from TM at runtime — the exact dependency the air-gap forbids.
- **No OTA; every change is a new store build.** Rejected: kills iteration speed during beta and forces testers through store re-review or re-sideload for trivial JS fixes.
- **Pure APK + self-hosted OTA, skip the stores entirely.** Rejected for the long run: the public launch requires real store presence. APK is retained as the TM fallback, not the only channel.
- **Expose an update CDN abroad and let TM reach it.** Rejected: contradicts ADR-0005's air-gap and adds an external runtime dependency.
