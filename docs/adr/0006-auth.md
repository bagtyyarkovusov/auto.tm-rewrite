# ADR-0006: Phone OTP + custom Android SMS gateway

- **Status**: Accepted
- **Date**: 2026-05-13

## Context

Turkmenistan does not have a reliable commercial SMS gateway (Twilio, MessageBird, etc. are unreachable or unreliable from TM Telecom). The previous AutoTM backend already addressed this with a homegrown SMS dispatch via physical Android phones — proven to work in production.

For the rewrite, we need:

- Phone-based authentication (TM users expect this; few use email)
- Reliable OTP delivery via SIM-equipped Android phones
- Different auth requirements for admins (desktop usage; SIM swap is a real risk)
- An auth model that supports anonymous browsing + auth-on-action

## Decision

### Mobile + public web users

**Phone OTP via custom Android SMS gateway.**

- User enters their phone number (`+993XXXXXXXX`, validated against TM mobile prefixes)
- API generates 6-digit OTP, stores hashed code with TTL (5 min), enqueues to SMS gateway
- SMS gateway picks an available phone (round-robin), sends via Android `SmsManager`
- User enters code; API validates, issues JWT access (15 min) + DB-hashed refresh token (30 days)
- Refresh token rotated on every refresh; old hash invalidated

### Admin users

**Phone OTP + TOTP 2FA.**

- Same OTP flow as users
- After OTP success, admin must enter a TOTP code (Google Authenticator / 1Password)
- TOTP enrolled on first admin login; backup codes generated and saved by admin
- Hard requirement: admin role cannot be granted without TOTP enrolled

### Anonymous browsing

- Listings, dealer pages, catalog, blog posts are **all readable without auth**
- API uses a global `JwtAuthGuard` with a `@Public()` decorator that skips it
- Mobile + web apps render anonymous state and prompt for login when user taps a gated action

### Action-gated auth

- Tapping a gated control (favorite, message, sell, save search) triggers a "Sign in to continue" bottom sheet
- After OTP success, the originally-intended action is **replayed** (`useDeferredAction` pattern)
- Profile tab without auth shows a single full-screen login CTA

### SMS gateway architecture

- `apps/sms-gateway` (Node service) coordinates 5-20 Android phones
- `apps/phone-agent` (Kotlin Android app) runs as a foreground service on each phone
- Phones connect to gateway via persistent WebSocket; gateway routes outbound SMS jobs round-robin
- Per-phone health monitor, per-SIM rate limit (80 SMS/day default), random inter-message delay
- Test mode env var `OTP_TEST_MODE=true` returns code in API response without sending — for CI

### Refresh token storage

- Bcrypt-hashed in `User.refreshTokenHash`
- Never stored plaintext
- One active refresh token per user at a time (rotation invalidates the old one)

## Consequences

### Positive
- No third-party SMS provider dependency
- Full control over delivery, rate limiting, abuse detection
- Cheap per OTP (just SIM credit, no per-message fee)
- TOTP 2FA defends admins against SIM swap

### Negative / accepted costs
- We operate physical phone hardware — operational burden (chargers, SIMs, monitoring)
- ~2-3 weeks of engineering to build gateway + agent properly
- Iceland to iOS background OTP autofill (`textContentType="oneTimeCode"`) works automatically; verify Android equivalent

### Neutral
- SIM enumeration / OTP bombing mitigated by rate limits and exponential backoff
- We accept that admin loss of phone + TOTP backup codes = locked out (acceptable for ~5 admins; recovery is a manual process)

## Alternatives considered

- **Email/password** — rejected: TM users are phone-first; email recovery is unreliable.
- **OAuth (Google / Apple)** — rejected: requires reaching foreign auth servers from TM users' devices; FCM works because OS handles it, but OAuth needs explicit user-initiated outbound which may be slow.
- **Magic link via email** — rejected: same problem as email + slow UX.
- **WebAuthn / passkeys** — too early; ecosystem not ready for TM market.
