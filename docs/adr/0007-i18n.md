# ADR-0007: i18n strategy (RU + TK + EN)

- **Status**: Accepted
- **Date**: 2026-05-13

## Context

AutoTM serves Turkmenistan. The market is multilingual:

- **Turkmen** (`tk-TM`, Latin script since 1993) — national language
- **Russian** (`ru-RU`) — widely spoken across generations
- **English** (`en-US`) — diaspora, dealer ops, professional users

We need a strategy that:

- Renders UI in the user's preferred language
- Handles user-generated content (listings, blog posts, messages) without forcing sellers to translate
- Supports search across mixed-language content (Cyrillic + Latin)
- Is air-gap-friendly (no translation APIs)

## Decision

### UI locales

Three locales supported from day 1: **Russian, Turkmen, English.**

- Translation files: `apps/<app>/src/locales/{ru,tk,en}.json`
- Library: `react-i18next` (mobile + web)
- Default locale: device locale if it matches one of {ru, tk, en}; else `ru`

### URL locale routing

- Locale appears in URL path: `/ru/listings/123`, `/tk/listings/123`, `/en/listings/123`
- Next.js App Router handles via `app/[lang]/...` segment
- `/listings/123` (no prefix) redirects to user's locale or `/ru/listings/123` as default

### Catalog data — trilingual columns

Reference data (brands, models, colors, regions) is curated and small (~5000 entries total). Each row has explicit translations:

```ts
Brand {
  id, slug,
  name_ru, name_tk, name_en,
  logoUrl, isActive
}

Color {
  id, hexCode,
  name_ru: "Чёрный",
  name_tk: "Gara",
  name_en: "Black"
}
```

Admin UI lets staff edit all three columns. Mobile/web render based on user locale: `color.name_${user.locale}`.

### User-generated content — single locale per item

Listings, blog posts, and chat messages are stored in **whatever language the user wrote them in**. We do **not** force sellers to provide translations.

- A listing has a single `title` and `description` field
- An optional `detectedLanguage` field auto-populated on save (via the `franc` library — small, offline)
- Detected language is metadata (used for analytics), not enforcement

This is honest UX: most TM users are bilingual (RU + TK) and read mixed content fluently. Forcing per-locale fields would deter sellers without benefit.

### Search across mixed-language content

Postgres native FTS handles Cyrillic + Latin via the `pg_catalog.simple` text search configuration, which tokenizes without language-specific stemming. A search for "BMW X5 2020" finds matching listings whether the description is in Russian or Turkmen.

### Number / date / currency formatting

- All times in DB stored as UTC
- Display formatted using `Intl.DateTimeFormat`, `Intl.NumberFormat` with user's locale
- Currency display in user's preferred currency (TMT / USD / AED), with admin-edited FX rate conversion shown if different from listing's original

## Consequences

### Positive
- Three-language UI from day 1 — no costly retrofit later
- Sellers experience zero friction (write in whichever language)
- Mixed-language search works without language-specific FTS configs
- Air-gap-friendly: no translation API calls

### Negative / accepted costs
- Translation maintenance burden — ~3-5k UI strings across 3 locales
- Some users will see UI in Russian + content in Turkmen (or vice versa) — acceptable since users are bilingual
- Catalog data updates require translating into 3 languages — slow but manageable for ~5000 rows

### Neutral
- We do not auto-translate content. If a future "translate this listing" feature is needed, it can be added with a server-side worker calling a translation service via TM Proxy PC.

## Alternatives considered

- **Russian only** — rejected: alienates Turkmen-preference users; "we'll add later" is a lie.
- **Multi-locale per listing (force translation)** — rejected: sellers won't comply; lowers listing volume.
- **Locale via cookie, not URL** — rejected: hurts SEO, deep linking gets confusing.
- **Custom FTS configs per language** — rejected: minor accuracy gain, big complexity (need to detect language, route to right config, handle mixed text).
