# admin — CONTEXT

> Current implemented state per [ADR-0019](../../../../../docs/adr/0019-context-md-describes-current-state.md). MLP moderation scope lives in `docs/prd/sprints/sprint-07-minimal-admin.md`. The full admin dashboard target capability lives in `docs/prd/features/40-admin.md` and is post-MLP per [ADR-0027](../../../../../docs/adr/0027-mlp-beta-scope.md).

## Purpose

Cross-cutting admin operations: audit log and moderation actions today. Staff media attribution, broadcast notification tooling, and the broader dashboard remain post-MLP. `apps/admin` consumes these admin routes plus the S9a inspection-interest aggregate route owned by `reports/`.

## Owns (entities + tables)

- `AuditLog` — id, actorId? (FK → User, onDelete: SetNull — admin user who performed the action; nullable to preserve audit history when an admin user is deleted), action (String — not yet an enum), targetType (String), targetId (String), details? (JSON), createdAt. Indexes on `(targetType, targetId)` and `(actorId, createdAt)`.
- `ContentReport` — id, reporterUserId? (FK → User, onDelete: SetNull — nullable after account deletion), targetType (String), targetId (String), reason (String), details? (String), status (String, default "pending"), reviewedById? (FK → User, onDelete: SetNull), reviewedAt? (DateTime), messageContext? (JSON), createdAt. Indexes on `(status, createdAt, id)`, `(targetType, targetId, status)`, and `(reporterUserId, createdAt, id)`. The `message` targetType is supported and populated through `CreateMessageReport` with surrounding conversation context.

## Invariants (enforced today)

- `AuditLog.actorId` references a User if non-null; on user delete, `actorId` is set to NULL (audit row survives for compliance).
- `AuditLog` is append-only at the schema level (no soft-delete; no schema-level update restriction — must be enforced at application layer when moderation ships in S7).
- `ContentReport.reporterUserId` is required at creation time (S7 does not create anonymous reports). Historical reports survive account deletion by nulling `reporterUserId`.
- `ContentReport.targetType` + `targetId` are polymorphic references with no DB FK. Target existence is validated at creation time through `ListingsReadPort` (for `listing` targets) and `IdentityReadPort` (for `user` targets).
- Report creation validates: active listings only (`sold` → `REPORT_TARGET_NOT_REPORTABLE`; missing/draft/archived/banned/deleted → 404); existing non-deleted users only (missing → 404); no self-reporting (own listing or own profile → `SELF_REPORT_NOT_ALLOWED`); suspended reporters are blocked (`USER_SUSPENDED`).
- Duplicate pending reports are deduped at application level: same `(reporterUserId, targetType, targetId)` while `status = pending` returns the existing report (HTTP 200, `reusedExisting = true`) instead of creating a new row. New reports return HTTP 201 with `reusedExisting = false`.
- `ContentReport.reason` enum values: `spam`, `scam`, `misleading`, `wrong_category` (listing-only), `harassment` (user or message only), `other` (requires non-empty trimmed details ≤ 1000 chars).
- `ContentReportCreated` event is emitted from `admin/` after a new report row commits. Duplicate reuse emits no event. S7 has no in-process consumers.
- Public report routes (`POST /api/v1/listings/:id/report` and `POST /api/v1/users/:id/report`) are authenticated with `JwtAuthGuard` (not `AdminGuard`). The public response shape is exactly `{ reportId, status, createdAt, reusedExisting }`.
- **Launch-safety flags** (S7/S9a closeout): `REPORT_ENTRY_ENABLED=false` blocks public report writes at the controller level (403 `FORBIDDEN` with `details.reason = "FEATURE_DISABLED"`) while admin report/audit reads remain available. `ADMIN_MODERATION_ACTIONS_ENABLED=false` blocks dismiss/ban/unban/suspend/unsuspend writes at the controller level (same 403 shape) while admin login, report list/detail, and audit list remain readable. `INSPECTION_INTEREST_ENABLED=false` is enforced in `reports/` for `POST /api/v1/listings/:id/inspection-interest`; `admin/` only exposes its public config flag. Flag checks are server-side environment config injected via `ConfigService`; disabled responses do not leak internal flag names.

## Ports consumed

- `ListingsReadPort` (`LISTINGS_READ_PORT`) from `listings/` — used by `CreateReport` to validate listing targets; used by `ListReports`, `GetReportDetail`, `ListAuditEntries`, `BanListing`, and `UnbanListing` for live listing target summaries and state checks
- `IdentityReadPort` (`IDENTITY_READ_PORT`) from `identity/` — used by `CreateReport` to validate user targets and check reporter suspension state; used by `CreateMessageReport` to check reporter suspension state; used by `ListReports`, `GetReportDetail`, and `ListAuditEntries` for live user/reporter/actor summaries
- `ConversationReportContextPort` (`CONVERSATION_REPORT_CONTEXT_PORT`) from `conversations/` — used by `CreateMessageReport` to verify the reported message exists, the reporter is a conversation participant, and to fetch surrounding messages; used by `ListReports` and `GetReportDetail` to resolve message target summaries and context
- `ListingsAdminPort` (`LISTINGS_ADMIN_PORT`) from `listings/` — used by `BanListing` and `UnbanListing` to perform transaction-scoped listing status transitions (`banActiveListing`, `unbanBannedListing`)
- `IdentityAdminPort` (`IDENTITY_ADMIN_PORT`) from `identity/` — used by `SuspendUser` and `UnsuspendUser` to perform transaction-scoped user suspension transitions (`suspendUser`, `unsuspendUser`)

## Shipped use-cases

- `CreateReport` — creates a `ContentReport` for `listing` or `user` targets after validating target existence/reachability, reporter suspension, and self-report rules; dedupes pending reports; emits `ContentReportCreated` for new rows only
- `CreateMessageReport` — creates a `ContentReport` for `message` targets after validating message existence through `ConversationReportContextPort`, reporter participation, reporter suspension, and self-report rules; persists surrounding conversation context in `messageContext`; dedupes pending reports; emits `ContentReportCreated` for new rows only
- `ListReports` — admin report queue with `OffsetPagination` (default 50 / max 100), default `status=pending`, `createdAt ASC, id ASC` sort, `status` + `targetType` filters, live `targetSummary` resolution; unavailable targets render `{ available: false, label: "Unavailable target" }`
- `GetReportDetail` — lean report detail with reporter/reviewer summary (deleted-user state), target summary (unavailable tolerated) for listing/user/message targets, live `pendingReportsOnTargetCount` and `reportsSubmittedByReporterCount`, admin-only `target.role` on user targets, and full `messageContext` (reported message plus surrounding messages) for message targets; returns 404 for missing report
- `ListAuditEntries` — admin audit log with `OffsetPagination` (default 50 / max 100), `createdAt DESC, id DESC` sort, `action`/`targetType`/`targetId` filters, live `actorSummary` (deleted admin vs operator script), short target label, one-line `reasonPreview`; missing targets tolerated
- `BanListing` — admin listing ban; accepts optional `reportId`; validates report order: unknown → 404, wrong-target → 400 `REPORT_TARGET_MISMATCH`, already-resolved → 409 `REPORT_ALREADY_RESOLVED`, pending-but-stale-target → 409 `REPORT_TARGET_NOT_ACTIONABLE`; direct-ban state conflict → 409 `MODERATION_TARGET_STATE_CONFLICT`; single-transaction report resolution (when provided) + listing mutation via `ListingsAdminPort.banActiveListing` + audit write; returns target state + `auditLogId` (+ `reportId`/`reportStatus=actioned` when report-backed)
- `UnbanListing` — admin listing unban; restores `banned → active` via `ListingsAdminPort.unbanBannedListing`; rejects `reportId`; state conflict → 409 `MODERATION_TARGET_STATE_CONFLICT`; single-transaction mutation + audit; returns target state + `auditLogId`
- `SuspendUser` — admin user suspend; accepts optional `reportId`; validates admin-target (`role = admin` → 403 `ADMIN_TARGET_NOT_MODERATABLE`) and self-moderation (target id === acting admin → 403 `SELF_MODERATION_NOT_ALLOWED`) before any mutation/report/audit; report-backed validation order identical to `BanListing`; direct-suspend state conflict (already suspended) → 409 `MODERATION_TARGET_STATE_CONFLICT`; single-transaction report resolution (when provided) + user suspension via `IdentityAdminPort.suspendUser` + audit write; returns target suspension state + `auditLogId` (+ `reportId`/`reportStatus=actioned` when report-backed)
- `UnsuspendUser` — admin user unsuspend; restores suspended → unsuspended via `IdentityAdminPort.unsuspendUser`; checks admin-target and self-moderation policies; rejects `reportId`; state conflict (not suspended) → 409 `MODERATION_TARGET_STATE_CONFLICT`; single-transaction mutation + audit; returns target suspension state + `auditLogId`
- `DismissReport` — admin report dismiss; accepts only pending reports; sets `ContentReport.status = dismissed`, `reviewedById`, `reviewedAt`; writes `CONTENT_REPORT_RESOLVE` audit row with `targetType = "content_report"`, `details.reportedTargetType`, and `details.reportedTargetId`; returns `reportId`, `status = dismissed`, `reviewedAt`, and `auditLogId`; already-resolved reports return 409 `REPORT_ALREADY_RESOLVED`

## Events emitted

- `ContentReportCreated` — emitted after a new `ContentReport` row commits. Payload: `{ reportId, targetType, targetId, reporterUserId, reason }`. Duplicate pending reuse emits no event.

## Planned additions (S7 MLP moderation + post-MLP dashboard)

Per [ADR-0019](../../../../../docs/adr/0019-context-md-describes-current-state.md), the MLP moderation items below are tracked in `docs/prd/sprints/sprint-07-minimal-admin.md`. Broader dashboard items are tracked in `docs/prd/features/40-admin.md` and require a post-MLP shaped bet.

- **`AuditLog.action` remains a String in S7.** Do not add a Prisma enum/backfill migration for the MLP. S7 defines canonical action constants in code/contracts: `ADMIN_BOOTSTRAP_PROMOTE`, `LISTING_BAN`, `LISTING_UNBAN`, `USER_SUSPEND`, `USER_UNSUSPEND`, `CONTENT_REPORT_RESOLVE`. Broader constants such as `DEALERSHIP_VERIFY`, `NOTIFICATION_BROADCAST`, `LISTING_PIN`, and `CATALOG_EDIT` are post-MLP unless their owning feature ships.
- **`AuditLog.details` carries S7 metadata** as structured JSON: required internal plain-text `reason` (trimmed before validation/storage, non-empty after trim, max 1000 chars after trim, internal line breaks preserved), `reportId?`, `reportedTargetType?`, `reportedTargetId?`, `before?`, `after?`, and action-specific fields. Admin UI renders reasons as escaped plain text. Do not add `beforeJson`, `afterJson`, or a top-level `reason` column in S7 unless implementation proves `details` is insufficient.
- **`ListAuditEntries` uses admin-table `OffsetPagination`** (`page`, `pageSize`; default page size 50, S7 effective max page size 100), defaults to `createdAt DESC, id DESC` for deterministic ties, and supports only `action`, `targetType`, and `targetId` filters in S7. List rows expose `id`, `createdAt`, `action`, `actorSummary`, `targetType`, `targetId`, a short live-resolved target label, and optionally a one-line escaped plain-text `reasonPreview`; they do not expose full `details` JSON in the table. Deleted/null actors render as "Deleted admin" for normal admin actions and "Operator script" for `ADMIN_BOOTSTRAP_PROMOTE`. Missing target lookups render "Unavailable target" while preserving the audit row. Invalid filters or invalid `page`/`pageSize` return HTTP 400 `VALIDATION_FAILED`; valid pages beyond the current result set return an empty row array with normal pagination metadata. CSV export, retention controls, actor/date-range filter UI, full-text search, and polished before/after diff are post-MLP dashboard work; S7 audit rows are append-only and retained indefinitely for the MLP.
- **`ContentReport` schema additions for S10 message reports**: `messageContext?` (JSONB) preserves surrounding conversation context for message-target reports. The `message` targetType is live via `CreateMessageReport`; S10 issue #249 shipped the public `POST /api/v1/conversations/:conversationId/messages/:messageId/report` route, reporter-participation validation, self-report rejection, and admin list/detail resolution. S7 MLP target types remain `listing` and `user`; `blog_post` is post-MLP because S7 excludes blog moderation.
- **S7 DB/query shape** stays small and index-backed: report pending queue uses `(status, createdAt, id)`, report target count/detail uses `(targetType, targetId, status)`, reporter history count uses `(reporterUserId, createdAt, id)`, audit default list uses `(createdAt, id)`, audit action filter uses `(action, createdAt, id)`, and audit target filter uses `(targetType, targetId, createdAt, id)`. S7 does not query `AuditLog.details` JSON or report details JSON, so it does not add JSON/GIN indexes for those fields. Duplicate pending report dedupe remains application-level; no partial unique index ships in S7.
- **S7 contract/runtime alignment**: API code imports S7 admin constants and schemas from `@auto-tm/contracts` instead of duplicating strings for report reasons, content-report statuses, audit actions, and `details.reason` values. Route-level validation may refine the shared offset pagination schema to enforce the S7 admin max page size of 100. API response timestamps are ISO strings matching contracts, not raw `Date` objects.
- **S7 transaction boundary**: `admin/` owns the moderation write transaction because it owns `ContentReport` resolution and `AuditLog`. Report-backed ban/suspend and direct ban/unban/suspend/unsuspend run report status updates, target mutation, and audit write inside one Prisma transaction. `ListingsAdminPort` and `IdentityAdminPort` keep target-state ownership but must participate in the caller's transaction or expose transaction-scoped adapters for S7 admin moderation; they must not open independent write transactions for these calls.
- **S7/S9a private-beta kill switches** are server-side environment/deployment config, not admin-managed DB state in the MLP. `REPORT_ENTRY_ENABLED=false` blocks public `POST /listings/:id/report` and `POST /users/:id/report` writes while admin report/audit reads remain available. `ADMIN_MODERATION_ACTIONS_ENABLED=false` blocks dismiss, ban, unban, suspend, and unsuspend writes while admin login, report list/detail, and audit list remain readable. `INSPECTION_INTEREST_ENABLED=false` blocks the S9a fake-door create route in `reports/` while admin aggregate reads remain available. Disabled writes return HTTP 403 `FORBIDDEN` with `details.reason = "FEATURE_DISABLED"` and must not leak internal flag names. UI hiding/disabled states are secondary; API enforcement is authoritative.
- **`StaffMediaAttribution` entity** (Phase 2 — pro photos/videos feature): { mediaKey, uploadedByStaff: bool, uploadedByUserId, uploadedAt, note? } — tracks media uploaded by AutoTM staff on behalf of sellers.
- **Application-level invariants**:
  - Every admin action that mutates user-visible state writes an `AuditLog` entry using a canonical string action constant
  - `actorId`, when non-null, must reference a `User.role = 'admin'` (TOTP-enrolled per ADR-0006 / ADR-0012). `ADMIN_BOOTSTRAP_PROMOTE` is the S7 exception: the operator script writes `actorId = null` because there is no authenticated admin session yet.
  - `ADMIN_BOOTSTRAP_PROMOTE` is written only by `packages/db/scripts/promote-admin.ts`, which requires `--phone` and `--reason`, supports optional `--dry-run`, exits zero as a no-op when the user is already `admin`, and exits non-zero with no audit row when no user matches. The script does not create users, create TOTP enrollment, set `adminTotpExpiresAt`, mint tokens, or bypass `AdminGuard`.
  - S7 admin moderation actions (`DismissReport`, `BanListing`, `UnbanListing`, `SuspendUser`, `UnsuspendUser`) require an internal plain-text reason; there is no admin reason enum, preset reason picker, templates, or classifier in the MLP.
  - `ContentReport.reporterUserId` is required at creation time; S7 does not create anonymous reports. Historical reports survive account deletion by nulling `reporterUserId` (`onDelete: SetNull` or equivalent), not by deleting the report.
  - Report validity is based on creation-time reporter checks plus review-time target actionability. Later reporter suspension or deletion does not auto-dismiss, auto-invalidate, or block actioning/dismissing existing reports. Deleted reporters render as "Deleted user"; suspended reporters remain normal reporter context if visible. S7 does not add reporter-trust scoring or abusive-reporter auto-invalidation.
  - `ContentReport.reviewedById` also uses nullable-after-delete semantics so old reviewed reports survive admin account deletion.
  - S7 does not store reporter/admin phone, name, or profile snapshots on `ContentReport`; deleted reporters/reviewers render as "Deleted user" in admin detail.
  - `ContentReport.targetType` + `targetId` are polymorphic target references with no DB FK to listing/user. Create-report use-cases validate target existence through the owning context before insert; admin action use-cases validate the target again before acting. If a target later disappears, report detail renders target unavailable while preserving the report row.
  - Report creation is owned by `admin/` because `ContentReport` is the moderation ticket. S7 keeps ergonomic resource-shaped public URLs (`POST /api/v1/listings/{id}/report`, `POST /api/v1/users/{id}/report`), but the controllers/use-cases live in `admin/` and map route params to `targetType` + `targetId`. Mobile entry points stay limited to active non-owner listing detail and visible non-self public user profile; there is no global report route/action and no message report route unless S6 is explicitly reshaped.
  - `admin/` validates report targets through `ListingsReadPort` / `IdentityReadPort`. `listings/` and `identity/` do not store reports, emit report-created events, or depend on moderation internals.
  - S7 public report target validation is narrow: listing reports require a currently `active` listing; user reports require an existing, non-deleted user that is reachable through a public surface. Suspended users may be reported only while still visible/reachable. Visible `role = admin` users are reportable through the same public user-report route; creation must not reveal or special-case staff role. Hidden or missing targets return HTTP 404 with the standard `NOT_FOUND` envelope. Visible but non-reportable listing states such as `sold` return HTTP 400 `VALIDATION_FAILED` with `details.reason = "REPORT_TARGET_NOT_REPORTABLE"`.
  - If S7 emits a report-created event, it is `ContentReportCreated` from `admin/` after a new report row commits. Payload is generic: `reportId`, `targetType`, `targetId`, `reporterUserId`, and `reason`. Duplicate pending reuse emits no `ContentReportCreated`. S7 ships no in-process consumers; future admin alerts/notification tooling consumes `ContentReportCreated`, not `ListingReported`.
  - Self-reporting is rejected in S7: `targetType = user` cannot target the reporter's own user id, and `targetType = listing` cannot target a listing whose `sellerId` is the reporter. Return HTTP 400 with the standard `VALIDATION_FAILED` error envelope and `details.reason = "SELF_REPORT_NOT_ALLOWED"`. Admins use direct admin action pages for internal moderation instead of creating public reports against their own targets.
  - S7 public report creation uses the existing global API throttler only. Do not add a report-specific per-user quota, quota table, or custom report throttling rule in the MLP; authenticated-only reports, suspended-user blocks, self-report rejection, duplicate pending dedupe, and no auto-hide-on-report are the S7 abuse controls. If beta shows queue spam across many targets, shape per-reporter quotas and reporting-rate analytics as post-MLP moderation-abuse work.
  - Duplicate reports are deduped in application code only while pending: same `reporterUserId` + `targetType` + `targetId` returns HTTP 200 with the existing pending report instead of creating another row; new reports return HTTP 201. Both use the same public response body: `{ reportId, status, createdAt, reusedExisting }`, with `reusedExisting = true` only for duplicate pending reuse. Duplicate reuse preserves the original `createdAt`, does not bump the report's queue position, and emits no report-created event. Different reporters may create separate pending reports for the same target. Closed reports (`dismissed`/`actioned`) do not block a later report from the same reporter. No DB partial unique index in S7. Public report responses do not expose other reporters' counts.
  - Public reporting is submit-only in S7. There are no public report history, status-detail, edit, retract, appeal, or support-ticket use-cases/endpoints; only admin routes can inspect and resolve `ContentReport` rows. If transparency, correction, or abuse-dispute workflows become necessary, shape them in a post-MLP trust/support PRD.
  - `ContentReport.reason = 'other'` requires non-empty `details` capped at 1000 chars after trimming leading/trailing whitespace; blank-after-trim details are invalid when details are required. Report details are stored as plain text, preserve internal line breaks, and do not support Markdown/HTML, linkification, rich previews, or a truncation contract. S7 stores reason enum values and lets the admin UI map human labels locally; it does not add PII scanning, translation, profanity filtering, or moderation classifiers for report details.
  - `ListReports` uses admin-table `OffsetPagination` (`page`, `pageSize`; default page size 50, S7 effective max page size 100), defaults to `status = pending`, sorts by `createdAt ASC, id ASC` for deterministic ties, and supports only `status` + `targetType` filters in S7. Invalid filters or invalid `page`/`pageSize` return HTTP 400 `VALIDATION_FAILED`; valid pages beyond the current result set return an empty row array with normal pagination metadata. List rows expose exactly `id`, `status`, `createdAt`, `reason`, `targetType`, `targetId`, and `targetSummary`. `targetSummary` is live-resolved through the owning context: listing targets use a display title such as year/make/model or listing title when available; user targets use a public display label when available; missing targets use an unavailable/deleted marker such as `{ available: false, label: "Unavailable target" }` while preserving `targetType` + `targetId`. List rows stay lean and do not include report `details` preview text, reporter identity fields, full target state, counts, actionability flags, or `target.role`; fetch report detail before rendering full details, reporter summary, target state, counts, actionability, or admin-target suspension controls. Assignment queues, severity filters, full-text search, and smart prioritization are post-MLP.
  - `targetSummary` and audit `actorSummary` are stable DTOs, not display-only strings. `targetSummary` preserves `available`, `label`, `targetType`, and `targetId`; unavailable targets use `available = false` with `"Unavailable target"`. Audit actor resolution distinguishes deleted authenticated admins from operator-script provenance for `ADMIN_BOOTSTRAP_PROMOTE`.
  - `GetReportDetail` returns lean S7 context only: reporter summary or deleted-user state, target summary or target-unavailable state, reason/details, status/timestamps, target current moderation state, `reportsSubmittedByReporterCount` when reporter still exists, and `pendingReportsOnTargetCount`. Detail target summaries may include listing title/year/make/model/status and, for user targets, admin-only `target.role` so `apps/admin` can explain/disable admin-target suspend; public report creation and report list rows never expose target role. Reporter/reviewer summaries are live minimal identity summaries or deleted-user state; `ContentReport` stores no phone/name/profile snapshots. `pendingReportsOnTargetCount` counts currently pending reports for the same `targetType` + `targetId`, including the current report if it is still pending. `reportsSubmittedByReporterCount` counts all historical S7 `ContentReport` rows by that reporter across listing/user targets and all statuses; omit it when `reporterUserId` is null after deletion. Both counts are computed live in `GetReportDetail`; do not add denormalized count columns, counter tables, or client-side aggregate state in S7. Admin UI renders report details as escaped plain text, preserving line breaks.
  - S7 report detail does not fetch rolling windows, trust scores, severity scores, conversation excerpts, deep reporter/owner history, reporter reputation, cross-report clustering, precomputed report-count read models, or other moderation-intelligence signals. Those require a post-MLP shaped moderation-intelligence bet.
  - `ContentReport.status = 'actioned' | 'dismissed'` requires `reviewedById` + `reviewedAt`
  - `DismissReport` is the only report-only resolution use-case: pending report -> dismissed, target unchanged, `CONTENT_REPORT_RESOLVE` audit row.
  - Audit targets follow the mutated thing. `DismissReport` mutates the report ticket, so its `CONTENT_REPORT_RESOLVE` audit row uses `targetType = "content_report"` and `targetId = reportId`, with `details.reportedTargetType` and `details.reportedTargetId` preserving the listing/user target. Report-backed `LISTING_BAN` and `USER_SUSPEND` audit rows target the moderated listing/user and carry `details.reportId`.
  - `AuditLog.details.before` / `details.after` stay minimal and structured in S7: dismiss records report status before/after; report-backed ban/suspend records the supplied report status before/after plus listing status or user suspension fields before/after; direct ban/unban records listing status before/after; direct suspend/unsuspend records user suspension fields before/after. S7 does not add a first-class before/after diff UI or top-level audit reason column.
  - `BanListing` and `SuspendUser` accept optional `reportId`. When present, validate the referenced report before any target mutation or audit write: unknown report id returns HTTP 404 `NOT_FOUND`; existing report whose `targetType`/`targetId` does not match the route target returns HTTP 400 `VALIDATION_FAILED` with `details.reason = "REPORT_TARGET_MISMATCH"`; matching but already-resolved report returns HTTP 409 `CONFLICT` with `details.reason = "REPORT_ALREADY_RESOLVED"`; matching pending report whose target is no longer actionable returns `REPORT_TARGET_NOT_ACTIONABLE`. Only the supplied matching pending report can be marked `actioned` in the same transaction as the moderation action and audit write. S7 does not cascade `actioned` or `dismissed` to other pending reports on the same target; those sibling reports remain pending for manual dismissal. Direct ban/suspend without `reportId` is allowed and does not touch reports, even when pending reports exist for the moderated target. No separate "action report" endpoint ships in S7.
  - Admin mutation endpoints return HTTP 200 with small JSON response bodies, not `204`. `DismissReport` returns `reportId`, `status = dismissed`, `reviewedAt`, and `auditLogId`. Report-backed ban/suspend returns target id/state, supplied `reportId`, `reportStatus = actioned`, and `auditLogId`, but no sibling report counts. Direct ban/suspend returns target id/state and `auditLogId` with no report fields. Unban/unsuspend return target id/state and `auditLogId`; their request schemas do not accept `reportId`.
  - Direct moderation actions revalidate current target state immediately before mutation. Missing/deleted targets return HTTP 404 `NOT_FOUND`. Existing targets in the wrong state return HTTP 409 `CONFLICT` with `details.reason = "MODERATION_TARGET_STATE_CONFLICT"` and current target state when known. Failed state-conflict requests write no audit row and perform no target mutation. This is separate from report-backed `REPORT_TARGET_NOT_ACTIONABLE`, which leaves a pending report to dismiss or refresh.
  - Pending reports remain dismissible if the target disappears or changes state before review. Report-backed ban/suspend revalidates current target actionability immediately before mutation: ban requires the listing still exists and is `active`; suspend requires the user still exists, is not deleted, and is not already suspended. If the report is still pending but the target is no longer actionable, return HTTP 409 `CONFLICT` with `details.reason = "REPORT_TARGET_NOT_ACTIONABLE"` and current target state when known. The failed request writes no audit row, does not mutate the target, and leaves the report pending.
  - Pending reports do not freeze target lifecycle in S7. Listing owners can still archive/delete listings through `listings/`, and users can still delete their accounts through `identity/`, even when pending reports exist. `admin/` does not expose a target-lock, moderation-hold, or legal-hold port in the MLP; if the target later disappears, report detail shows target unavailable and only dismiss remains actionable.
  - Report-backed actionability is current-state only. A still-pending report is not invalidated by an earlier direct ban/unban or suspend/unsuspend cycle; if the target is currently actionable at review time, the report can be actioned. S7 does not add moderation epochs, report invalidation snapshots, or staleness-lock fields.
  - Pending reports do not expire or auto-dismiss in S7. They remain `pending` until `DismissReport` or a supplied matching report-backed `BanListing`/`SuspendUser` resolves them. Do not add age-based report states, SLA timers, scheduled cleanup jobs, or auto-close behavior in the MLP; age filters, escalation, and auto-close are post-MLP moderation-operations/dashboard work if queue volume requires them.
  - S7 has no report assignment/claim workflow. All report resolution use-cases conditionally update only `ContentReport.status = 'pending'`; if another admin already resolved the report, return HTTP 409 with the standard `CONFLICT` error envelope, `details.reason = "REPORT_ALREADY_RESOLVED"`, and the current report status. Do not overwrite `reviewedById`/`reviewedAt`.
  - For ban/suspend with a matching pending `reportId`, supplied-report resolution, target mutation through the owning context port, and audit write are one transaction: all succeed or all roll back. Failed report-backed validation writes no audit row and performs no target mutation. If target mutation succeeds but audit write fails, the target mutation rolls back. If audit write would succeed but target mutation fails, no audit row is committed. Sibling pending reports on the same target are not part of the transaction. The losing side of a concurrent resolution writes no audit row and performs no target mutation.
  - Direct ban/unban/suspend/unsuspend without `reportId` are also atomic with audit: target mutation and audit write commit together or roll back together.
  - S7 does not add idempotency keys for admin moderation mutations. Double submits rely on current-state validation: if the first request succeeds, the second returns `REPORT_ALREADY_RESOLVED` for the same report or `MODERATION_TARGET_STATE_CONFLICT` for the changed target state.
  - `BanListing` / `UnbanListing` orchestrate moderation in `admin/`, but they do not write listing rows directly. Listing status transitions are owned by `listings/` through `ListingsAdminPort.banActiveListing` and `ListingsAdminPort.unbanBannedListing`.
  - `SuspendUser` / `UnsuspendUser` orchestrate moderation in `admin/`, but they do not write user rows directly. User suspension state is owned by `identity/` through `IdentityAdminPort.suspendUser` and `IdentityAdminPort.unsuspendUser`.
  - S7 user moderation is not admin account management. `SuspendUser` / `UnsuspendUser` reject `role = admin` targets with HTTP 403 `FORBIDDEN` and `details.reason = "ADMIN_TARGET_NOT_MODERATABLE"`; attempts by the acting admin to suspend/unsuspend their own account return HTTP 403 `FORBIDDEN` with `details.reason = "SELF_MODERATION_NOT_ALLOWED"`. These policy failures write no audit row, mutate no user state, and do not resolve a supplied report. S7 has no admin demotion/deprovision UI; compromised, mistaken, or abusive admin handling is an operator runbook/session revocation or post-MLP admin-account-management concern.
  - A pending report may target a visible admin account. It remains a normal report ticket that can be dismissed, but report-backed suspend follows the same `ADMIN_TARGET_NOT_MODERATABLE` policy failure. Do not add public staff-role leakage, special public admin-report errors, or automatic staff-abuse workflows in S7.
  - Direct ban/suspend UI in S7 is reachable only through known-target action pages (`/listings/:id`, `/users/:id`) or report detail links. Full admin listing/user indexes and search are post-MLP dashboard work.
  - Direct ban/suspend without `reportId` stays allowed and does not resolve pending reports. S7 does not compute or expose pending-report warning counts for these direct-action confirmations.
  - Unban/unsuspend discoverability in S7 relies on known target id, report-detail links, or audit-log target links. Do not add banned-listing or suspended-user queues for the MLP; those are post-MLP dashboard filters.
  - S7 report resolution is internal: no reporter notification/feed item is emitted, reporters cannot track report status, and admin free-text reasons are not exposed to reporters, listing owners, suspended users, or public users.
  - Reported listing owners and reported users do not receive report metadata in S7: no report count, reason/details, reporter identity, report status, or admin notes in public, owner, or account surfaces. If a target is moderated, owning contexts expose only generic banned/suspended state.
  - S7 report creation does not mutate the target listing's status or public visibility; report count alone never auto-hides a listing
  - S7 listing bans do not auto-close conversations. They block new contact/new messages for the banned listing and leave existing conversation history readable.
  - S7 moderation events have no user-facing consumers: no push, no in-app feed item, no conversation auto-close, no owner notification, and no reporter notification. S7 enforcement comes from synchronous state checks against listing status and `User.suspendedAt`. If emitted, moderation events are emitted only after the outer admin-owned transaction commits; they are never emitted inside a transaction that can still roll back.
  - S7 admin confirmation UX must not require computed "affected listing/conversation" aggregate counts. Confirmation copy is static per action because suspend does not auto-ban listings and listing ban does not close existing conversations.
  - S7 listing ban/unban is a narrow state pair: only `active -> banned -> active`. No `previousStatus` field/table is added in the MLP. Non-active ban attempts and non-banned unban attempts use `MODERATION_TARGET_STATE_CONFLICT`.
  - Banned listings are omitted from public feed/search/favorites, and non-owner public detail reads return `NOT_FOUND`. Owner-scoped listing surfaces may show the listing with a generic banned notice only. Owner listing mutation routes do not edit, attach/remove/reorder media, mark sold, archive, republish, or delete banned listings until admin unban; owner archive/delete is not a workaround for admin ban.
  - Unban restores only `banned -> active`. It does not clear favorites, emit saved-search notifications, or resolve/dismiss pending reports.
  - S7 user suspend/unsuspend is a narrow current-state pair owned by `identity/`: for non-admin targets only, suspend sets `User.suspendedAt`, `suspendedById`, and internal `suspensionReason`; unsuspend clears the same fields. Already-suspended suspend attempts and already-unsuspended unsuspend attempts use `MODERATION_TARGET_STATE_CONFLICT`. AuditLog owns history; no duration/expiry model is added in the MLP.
  - Suspended-user enforcement is synchronous and outside audit: blocked authenticated marketplace mutations return HTTP 403 `FORBIDDEN` with `details.reason = "USER_SUSPENDED"` and generic client copy. Suspension does not auto-ban, hide, archive, or delete the user's listings; admins ban listings separately when needed. Existing conversations remain readable, but new contact/messages are blocked when either participant is suspended.
  - Post-MLP bulk moderation fans out to one `AuditLog` row per target with shared `details.batchId`/`details.batchReason`; do not collapse multiple targets into one audit row whose only target history is a `targetIds` array.
- **Admin actions catalog (MLP S7 + post-MLP expansion)**:

  | Action | Effect |
  |---|---|
  | `ADMIN_BOOTSTRAP_PROMOTE` | Operator script promotes an existing OTP-verified user to pending admin assignment before TOTP enrollment; audit target is the promoted user, with `actorId = null` |

  | `USER_SUSPEND` | For currently unsuspended users: sets `User.suspendedAt`, `suspendedById`, and internal `suspensionReason`; blocks future authenticated marketplace mutations; optionally action-resolves a matching pending user report |

  | `DEALERSHIP_UNVERIFY` | Clears `verifiedAt` |
  | `NOTIFICATION_BROADCAST` | Broadcasts via `notifications/` |
  | `CATALOG_EDIT` | Add / edit / remove catalog rows |
  | `CONTENT_REPORT_RESOLVE` | Dismiss a pending content report without mutating its reported listing/user; audit target is the `content_report` row |
