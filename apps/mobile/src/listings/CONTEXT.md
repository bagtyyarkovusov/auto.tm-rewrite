# Mobile listings

This area contains create-wizard state, draft persistence, upload staging, edit-save orchestration, discovery state, and listing presentation. The create route and edit route have different orchestration; inspect both before consolidating shared UI. Server lifecycle and contact rules belong to [API Listings](../../../api/src/modules/listings/CONTEXT.md).

## Important constraints

Create flow uses the wizard machine and autosave; edit flow computes and sequences changes against an existing listing. Shared contract schemas own validation. Do not make the UI's visual step number a second validation model. Photo UI receives its actual props from the live component interface; old Step2Photos warnings and historical refactor plans are not current requirements.

Publishing depends on required fields, contact verification, and successful media attachment. A file appearing in a preview does not prove it was uploaded or attached. Preserve retry state and draft reconstruction, and inspect the queue, publish-gate code, and tests when changing navigation or autosave timing.

The condition disclosure is one required Yes/No question, **Damaged / needs repair**, plus optional **Known issues** ([ADR-0052](../../../../docs/adr/0052-seller-condition-disclosure-is-damaged-plus-known-issues.md)). Step 4 leaves it unanswered until the seller picks one, and the shared `StepSpecsSchema` blocks the step (`wizardErrors.damagedRequired`) until then. A legacy Listing without an answer enters edit at the specs question before the seller can save. A submitted disclosure replaces Known issues, so clearing the input removes the saved text. Listing detail shows it under "Condition, as stated by the seller" and renders nothing when a Listing has no answer.

Listing detail follows the approved Auto.ru content order with AutoTM tokens: photos and numeric counter, title, price, date/city, six key specifications followed by rows, expandable seller description, seller-stated condition, Seller card, Report, and public-number/date footer. Ask the seller, card-cache loading and photo-viewer expansion remain separate slices. The route owns the sticky Call/Message or owner Edit/Mark sold bar, measured gallery scroll threshold, header actions and Report sign-in/replay. The owner menu holds Archive, Share and Delete, plus Republish for archived Listings. Views and saves appear only in the owner status card. Sold/archived buyers retain the banner, muted price and similar brand/model link, with contact, Favorite and Report hidden. A 404 offers Home and Back.

The Seller card uses the real display name or Private seller, join month, and city/place. It has no Phone verified badge; Call carries the SMS-verification caption under ADR-0056. VIN remains a specification row when present; the decoding section renders only for `vinHistory.decoded === true`, with no empty state under ADR-0053. ADR-0057 keeps the inspection component, hook and tests unused: detail no longer renders its entry or reads the inspection config, and publishing no longer requests its sheet. The API endpoint and decoder code remain unchanged.

Picker URIs are copied into persistent temporary storage before parallel compression because iOS may reclaim picker cache files under memory pressure. The compressor copies its result into staging, verifies the destination, and cleans temporary files best-effort. Preserve copy rather than cross-directory move; earlier iOS failures motivated that choice. Overlapping compression/upload operations use reference counters, since a boolean can clear while another operation is still active.

The compressor currently uses the contextual ImageManipulator chain. Consult current Expo docs before an SDK change; historical API notes cannot establish present library support. Staging cleanup is local-device cleanup, distinct from the worker's broad orphan-cleanup queue.

Search/filter UI separates editing state from applied query state. Check the stores, serializers, query keys, and API ranking adapter together when changing filters or result counts. Approved discovery requirements are in the Search specification, not old planned-refactor notes.

Home (`app/(tabs)/(search)/index.tsx`) is the root of the Search tab's own stack, anchored at `index` so a deep link still has Home underneath. `AutoTmTabBar` always emits `tabPress` and navigates only to an unfocused tab, so re-tapping Search pops to Home while other tabs keep their history. Home has no filters: a Brand/model card with the live count and a two-column New listings grid of `ListingGridCard`. Search remains an interim stand-in. Results keeps applied filters and one of the six approved sort orders in route search params, so deep links and Back restore the same search. Its header reads the live matching count and TMT range. Condition and removable city/price/year chips commit in place, with the chips floating at the bottom once the header scrolls away. A single brand/model card shows the chosen brand's `CarBrandLogo` (its letter when there is no logo; the generic car only when no brand is chosen), opens the current ticked models and can clear the selection. "Reset filters" on a no-match Results and "Reset all" in the filter sheet clear the filters but keep the current sort. The list stays mounted behind Listing and sign-in navigation, preserving its native scroll position. Results uses `ListingLargeCard`: a photo area that follows the Listing's photos (none gives one "No photos" frame, one gives a single wide photo, two or more give a 62%/38% two-photo grid; the 📷 count shows only above one photo), TMT price, available mileage/gearbox/fuel names, one-line brand/model/year, city/date, and a bottom-right favorite action, plus a skeleton with one wide photo block. A signed-out ♡ on a card stores a pending Favorite; `useFeedFavoriteReplay` finishes it at screen level when the owning Home or Results screen regains focus, because the tapped card may no longer be mounted. Feed cards and Listing detail share `useListingFavorite`. `setFeedFavorited` writes a ♡ state only into signed-in cached feed pages, because a silent sign-out keeps the query cache and Home would otherwise show the previous User's ♥.

The Brand picker (`brands`) picks exactly one brand: a search field sent to the catalog search (any spelling; the picker keeps only brand results, and matches one letter locally because the API ignores it), then Recent, Popular with counts from `/listings/filter-options/brands`, and A to Z. Every row shows `CarBrandLogo`, the uploaded logo tinted with the theme foreground, or the brand's first letter when there is none or it fails to load; a no-affiliation notice closes the list. Tapping a brand pushes the Model picker (`models?brandId=&modelIds=`), which ticks any number of models; none means every model of the brand. Opened from Results, confirmation dismisses back to that existing Results route, preserving its other filters and sort. From Home, "Show N listings" dismisses the pickers and opens Results; "More filters" opens Results with the filter sheet open, because the full-screen Search parameters form (#371) has not landed; "Change brand" dismisses back to the Brand picker. Inside the filter sheet, `BrandModelFilterControl` opens the same pickers in Done mode, with no Recent or More filters, and Done writes the brand and models back to the form without applying it. `pickerActions` owns these per-mode routes, `resultsParams` the picker selection params and `resultsRouteState` the complete persistent applied Results search (still accepting the single `modelId` from "See other Brand Model"), and `useBrandPicker`/`useModelPicker` what each picker shows. Recent (`recentSearches`) is the last 10 confirmed choices, brand-only ones included, de-duplicated by brand and model set with the repeat moved to the top. It lives in AsyncStorage on the device only and is cleared from the Brand picker. It is not a saved search and makes no API call. A failed device write keeps the in-memory list for the session.
